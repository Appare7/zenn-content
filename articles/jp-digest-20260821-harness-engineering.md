「プロンプトエンジニアリング」「コンテキストエンジニアリング」に続いて、2026年夏に急に増えたのが「ハーネスエンジニアリング」です。この記事は、研究者の個人ブログ・海外の技術メディア・開発元のエンジニアリングブログといった複数の海外記事と公式発表を読み込んで、日本の現場目線で組み直したものです。結論から言うと、伸びしろはもうモデルの中だけにはない。モデルの「外側」にあるんです。

![](/images/jp-digest-20260821-harness-engineering/figure1.png)

## ハーネスエンジニアリングとは？「モデルの外側」を設計する話

2026年7月4日、研究者のLilian Weng（リリアン・ウェン）が自身のブログ Lil'Log に「Harness Engineering for Self-Improvement」という記事を公開しました。読了目安31分の長文で、約35本の論文をまとめたものです。

Wengは現在 Thinky（シンキー）というスタートアップの共同創業者でもあります。その記事でのハーネス（harness／エージェントを動かすための土台・足場）の定義は、かなり広いです。

「ベースモデルを取り囲み、実行を統率するシステム。モデルがどう考え計画し、ツールを呼んで行動し、コンテキストを知覚・管理し、成果物を保存し、結果を評価するかを決める」

つまり、モデルそのものではなく、モデルを走らせる外側ぜんぶ。Wengは、Claude Code や Codex のような成功したコーディングエージェント製品こそが、ハーネスの重要さを示している、と書いています。

背景には RSI（recursive self-improvement／再帰的自己改善）があります。この概念自体は古く、I. J. Good が1965年に「超知能機械」として定義し、Yudkowsky が2008年に「recursive self-improvement」という言い方をしました。

ただ、Wengの現代的な解釈はもっと地に足がついています。自己改善は「モデルが自分の重みを直接書き換える」だけの話ではなく、訓練パイプラインやデプロイシステムを改善することも含む、という見方なんです。

たとえるなら、モデルが「選手」なら、ハーネスは「コーチ・練習メニュー・スコアブック・ジムの設備」ぜんぶ。選手を入れ替えなくても、周りを変えると成績が変わる。エージェント開発で起きているのは、まさにこれですよね。

## プロンプト／コンテキスト／ハーネス、何が違うの？

まず、プロンプトエンジニアリングは、1回の入力の書き方を工夫する層です。「どう頼むか」を詰める世界。

コンテキストエンジニアリングは、限られたコンテキストウィンドウ（モデルが一度に読める範囲）に、何をどう載せるかを設計する層です。過去ログ、仕様、コード、検索結果、メモリ。どれを入れて、どれを捨てるか。

ハーネスエンジニアリングは、さらに外側です。そもそもループ全体を設計します。思考と計画、ツールの呼び方、コンテキストの管理、成果物の保存、結果の評価まで含みます。

外側の層ほど守備範囲が広い、というわけです。プロンプトをいくら磨いても、ループの設計が悪いと頭打ちになります。エージェントが毎回同じミスをする、途中成果を失う、テストを勝手に消す。こういうのはプロンプトだけで殴るより、ハーネスで縛ったほうが効くことが多いです。

![](/images/jp-digest-20260821-harness-engineering/figure2.png)

## ハーネスの中身は5つ。まずはここを疑う

Wengの定義を分解すると、まず見るべき場所はこの5つです。

1. 思考と計画（どう考え、どう段取りするか）
2. ツールの呼び出しと行動
3. コンテキストの知覚と管理
4. 成果物（アーティファクト）の保存
5. 結果の評価

![](/images/jp-digest-20260821-harness-engineering/figure3.png)

さらに、Wengはハーネスの設計パターンとして、次の3つを挙げています。

- パターン1：ワークフロー自動化。計画→実行→観察→改善というゴール指向のループを回す。
- パターン2：ファイルシステムを永続メモリとして使う。状態をファイルに置いて持ち越す。
- パターン3：サブエージェントとバックグラウンドジョブ。並列に走らせて監視する。

ここ、実装している人ほど「それ、もうやってるかも」となるはずです。ただ名前がつくと、設計対象として見やすくなるんですよね。

## 自己改善のやり方は5パターンある（論文35本の見取り図）

Wengが整理した最適化のカテゴリは5つあります。

- コンテキストエンジニアリング
- ワークフロー設計
- 自己改善するハーネス
- 進化的探索
- モデルの重みとの同時最適化

代表的な手法も、名前だけ見るとかなりにぎやかです。

- ACE（Agentic Context Engineering）：コンテキストを「進化するプレイブック（作戦帳）」として扱い、生成役・振り返り役・整理役で回す。
- MCE（Meta Context Engineering）：コンテキストの「管理のしかた」と「中身」を分けて、二段構えで最適化する。
- Meta-Harness：ハーネスのコードそのものを最適化する。コーディングエージェントがより良いハーネスを書いて評価する。TerminalBench-2 で改善が出たとされている。
- AFlow：ワークフローのグラフ上でモンテカルロ木探索（可能性の木を探索する手法）を回す。
- STOP（Self-Taught Optimizer）：改善役自身を再帰的に改善する。改善された改善役は、遺伝的アルゴリズム、部分に分解して直す、複数プロンプトを試して当たりを引く、といった戦略を自分で見つけた。
- DGM（Darwin Gödel Machine）：LLM（large language model／大規模言語モデル）ベースのコーディングエージェントが自分のハーネスを書き換える。
- 他に ADAS、Self-Harness、AlphaEvolve、ShinkaEvolve、AI Scientist、AHE（Agentic Harness Engineering）といった名前も並ぶ。

名前が多すぎて目が滑るんですが、やっていることはかなり共通しています。モデルは固定したまま、周りをいじって強くする。まずはそう捉えると読みやすいです。

## 数字で見る：ハーネスを変えるとどれくらい伸びる？

ここからの数字は、Wengの記事が引用しているベンチマーク数値です。各論文が報告した数字で、条件はそれぞれ違います。横並びで単純比較するというより、「外側を変えると伸びる余地があるんだな」くらいで見てください。

- DGM（Darwin Gödel Machine）：DGMが発見したエージェントは、SWE-bench Verified で 20% → 50%、Polyglot で 14.2% → 30.7%。手作りのエージェントと同等かそれ以上になった。
- RE-Bench：人間の専門家は8時間の試行のうち82%で非ゼロのスコアを出し、24%が強い参照解に匹敵するか上回った。一方で、2時間という短い予算ではAIエージェントのほうが人間の4倍のスコアを出した。
- MLE-bench：o1-preview に AIDE というスキャフォールディング（足場）を組み合わせると、16.9%のコンペで Kaggle の銅メダル相当以上に到達した。
- PaperBench：当時の最高モデル（Claude 3.5 Sonnet）は約21%で、機械学習の博士たちには及ばなかった。採点用のルーブリック（採点基準）は全部で8,316項目。
- CORE-Bench：当時の最高エージェント（GPT-4o と GPT-4o-mini）は、いちばん難しいタスクで21%どまり。

RE-Benchの「短い時間ならAIが4倍、長い時間なら人間が勝つ」は、いまのエージェントの得意・不得意をよく表しています。短距離走は強い。でも長丁場はまだ人間。そんな感じですね。

## 現場のベストプラクティス：初期化係と実装係を分ける

Anthropic のエンジニアリングブログ「Effective harnesses for long-running agents」では、長時間動くエージェントの組み方が紹介されています。

ポイントは、エージェントを2種類に分けること。初回セッションだけ動く「初期化エージェント」と、2回目以降の「コーディングエージェント」です。プロンプトも別にします。

初期化エージェントが最初に作るものは、`init.sh` スクリプト、エージェントが何をやったかを記録する `claude-progress.txt`、そして最初の git コミット。さらに詳細な機能要件のファイルです。

機能一覧は構造化されたJSONファイルで書きます。claude.ai のクローンを作らせた例では、機能が200個以上並びました。各機能は最初「failing（未達）」として印を付け、手順を明記しておきます。

コーディングエージェントには、かなり強く釘を刺します。原文の指示はこうです。

「テストを削除したり編集したりすることは許容できない。機能の欠落やバグにつながりうるからだ」

毎回のセッションは、進捗を説明的なコミットメッセージで git にコミットし、進捗ファイルにサマリを書いて終わります。

次のセッションの立ち上がりは、`pwd` を実行し、git のログと進捗ファイルを読んで状況に追いつき、いちばん優先度の高い未完了の機能を選ぶ、という順番です。

テストはブラウザ自動操作のツールを使って、人間のユーザーと同じようにやらせます。最初のセッションでは、新機能に手を付ける前に基本的なE2Eテスト（画面から通しで動かすテスト）を1本走らせます。

やっていることは、優秀だけど毎朝記憶を失う新人にプロジェクトを引き継ぐ手順そのものです。進捗ファイルとgitログが「申し送りノート」になっているんですね。

![](/images/jp-digest-20260821-harness-engineering/figure5.png)

### システムプロンプトを8割削った話

Developers Digest（2026年7月26日）は、同じくAnthropicの動きを報じています。

Anthropic は Opus 5 と Fable 5 向けに、Claude Code のシステムプロンプトを80%以上削除しました。それでコーディングの評価スコアに劣化は出なかった、という話です。

転換の中身は、かなりハーネスっぽいです。

- ルールから判断へ。「複数段落のdocstringを書くな」のような明示的な制約をやめ、「周囲のコードと同じように読めるコードを書く」のような原則に置き換えた。
- 使用例からツールのインターフェース設計へ。
- 段階的な開示。詳細な指示を最初に全部読ませず、必要になったときだけ読み込ませる。
- 重複した指示の削除。
- 自動メモリ。
- プレーンなmarkdownの仕様書から、HTMLの成果物・テストスイート・コードベースそのものといったリッチな参照へ。

一方で、Hacker News では197ポイント・133コメントの議論になりました。反発もあり、自動メモリについては「裏で勝手に何かがメモリに追加されるのは絶対に嫌だ」という声が出ています。自律性が上がるぶん、もっともらしい間違いを見抜く開発者の判断力が要る、Opus 5 でミスや回避策が増えたという報告もある、という批判も紹介されています。

## 頭と手を切り離したら、p50が6割速くなった

Anthropicのエンジニアリングブログ「Scaling Managed Agents: Decoupling the brain from the hands」では、ハーネスのアーキテクチャ変更が紹介されています。

もともとは、ハーネス、つまり脳と、サンドボックス・セッション保存、つまり手を、1つのコンテナに同居させていました。

そのせいで、コンテナが落ちるとセッションごと消えてデバッグもできない、顧客のVPC（仮想プライベートクラウド）につなぐにはネットワークピアリングが要る、セッションのたびにコンテナ起動コストを前払いする、という問題がありました。

直し方は3つです。

- ハーネスをステートレスにして、`execute(name, input) → string` という汎用インターフェース越しにサンドボックスを呼ぶ。
- セッションのイベントをハーネスの外に耐久保存し、`wake(sessionId)` で復帰できるようにする。
- サンドボックスを差し替え可能にして、実行環境そのものをツールとして扱い、失敗は捕まえてリトライする。

結果、TTFT（time-to-first-token／最初のトークンが返るまでの時間）は p50（中央値）でおよそ60%減、p95（遅いほうから5%目）では90%超の減少。さらに、認証情報がClaudeの生成コードの走るサンドボックスに届かなくなり、セキュリティ面でも良くなりました。

OSがハードウェアを仮想化していった歴史と同じ形だ、という言い方もされています。

これはモデルを一切触っていない改善です。ハーネスの話がなぜ効くのか、いちばん分かりやすい例かもしれません。

## ハマりどころ：評価なき自律は「速く壊す」だけ

Wengは、ハーネスや自己改善には課題もあると書いています。大事なので、ここはざっと並べます。

1. 評価器が弱い。多くの研究上の主張には、速くて正確な検証器がそもそも存在しない。
2. コンテキストとメモリのライフサイクル管理。自律的に動くエージェントのメモリは膨らみ続ける。
3. ネガティブな結果のバイアス。文献は成功例に偏っている。
4. 多様性の崩壊。開放的な探索を続けるには、崩壊を防ぐ仕組みが要る。
5. リワードハッキング（報酬の抜け穴探し）。Wengの提言は、評価器と権限管理は、ハーネスを進化させるループの「外」に置くべき、というものです。そこに held-out テスト（学習に使っていない取っておきのテスト）、トレース（実行履歴）の監査、人間のレビューを添える。システムが自分の評価器をいじれるなら、評価器を騙すことを覚えるからです。
6. 長期的な成功の測りにくさ。保守性や後方互換性のような話は短期の点数に出ない。
7. 人間の役割。Wengの言い方はこうです。「人間はスタックの上に移動すべきであって、ループから外れるべきではない」

![](/images/jp-digest-20260821-harness-engineering/figure6.png)

海外メディア Lilith AI は2026年7月4日、この流れをこう読み解いています。自己改善とは、モデルがこっそり自分の重みを書き換えることではなく、ツール・コンテキスト・メモリ・評価を管理する周辺システムを良くしていくこと。チームが作るべきプロダクトは、プロンプトの微調整ではなくハーネスそのもの。

本番のエージェントには境界が要ります。何を実行してよいか、中間の作業をどこに残すか、過去の文脈にどうアクセスさせるか、いつ止めるか、何をもって成功とするか。

コーディングエージェントや自動研究のような構造化された環境は、理想的な試験場になります。失敗が観測でき、計測できるからです。

「評価のない自律は、より速く壊すための手段でしかない」

設計の悪いメモリはエラーを永続化させます。隔離、監査できるトレース、評価の枠組みがないと、能力の拡張は「自信ありげな退行」になってしまう。進歩のシグナルは派手なデモではなく、再現できるログと、追える指標。ここ、かなり現場っぽいですよね。

## まとめ：明日いじれるのは、たぶんハーネスのほう

モデルの乗り換えは、どうしても待ちの時間が長いです。でもハーネスは今日から書き換えられます。

最初の一歩として現実的なのは、進捗ファイルとgitログで状態を持ち越すこと、テストを「消せない前提」にすること、評価をエージェントの外側に置くこと。このあたりは、すぐ試せます。

Wengの見立てとして、Latent Space が引いた本人の投稿にはこんな一文があります。

「RSIの未来がどれだけハーネスに依存するかを予測するのは難しい。おそらくハーネスエンジニアリングは自己改善の方向へ進化し、自動研究を可能にし、ひいてはより賢いモデルにつながる」

ただし本人は、ゴールとコンテキストを指定する必要がなくなることはない、とも書いています。ここは人間の仕事として残るんです。

というわけで、次にエージェントが微妙な動きをしたとき、プロンプトだけを疑うのは少し早いかもしれません。自分のエージェントのハーネス、どこが一番ボロいですか？
