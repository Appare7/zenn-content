## 🧩 1. サブエージェントとは：別の窓で働いて、要約だけ持ち帰る

✅ 一言で言うと、サブエージェント（subagent／メインのClaudeが仕事を任せる専門の助手）は、**自分専用のコンテキストウィンドウ（Claudeの作業記憶）で動いて、要約だけをメインに返す存在** なんです。途中でファイルを読んだり、検索したり、ツールを呼んだりした記録は、全部サブの窓の中に隔離されます。メインに残るのは、こちらが書いた依頼文と、返ってきた要約だけですね。

![](/images/claude-code-subagents-course-japanese/figure02.png)
*サブに渡るのは依頼文だけ、戻るのは要約だけ。途中のツール呼び出しはサブの窓の中に閉じます*

サブエージェントが受け取るものは、2つしかありません。

1. **設定ファイルに書いたカスタムシステムプロンプト**（system prompt／その助手に最初から与えられている役割の説明文）
2. **親（メインのClaude）が書いたタスクの説明**

これだけなんですよ！メインがそれまでに読んだファイルも、会話の流れも、サブには渡りません。そして仕事が終わったら、サブの会話は捨てられます。まっさらな状態で受け取って、結果を渡して、消える。サッカーで言えば、偵察に出したスカウトが、相手チームのレポートだけ持って帰ってくる感じですね。試合を90分見た記憶はスカウトの中にあって、監督の手元には報告書だけが残る。

⚠️ 代償もはっきりしています。**どうやってその結論に至ったかが、見えなくなる** んです。レポートに「相手の右サイドが弱い」と書いてあっても、どの場面を見てそう判断したかは分からない。前回の記事では「ここはトレードオフです」と一言で済ませていたんですが、この代償が後々どこで効いてくるのかは、このコースを受けるまで分かっていませんでした。正直、前回は「別の窓」という言葉だけで分かった気になっていた。

### 無しだとどうなるか

コースの例が分かりやすかったので、そのまま紹介しますね。「返金を扱うサービスはどれ？」という質問をメインに投げたとします。サブエージェント無しだと、Claudeは15ファイルほど読んで、検索して、呼び出しを辿って、ようやく答えに辿り着きます。その15ファイル分の中身が、全部メインのコンテキストに積まれるわけです。質問はひとつなのに、作業記憶はごっそり埋まってしまうんですね。

![](/images/claude-code-subagents-course-japanese/figure03.png)
*同じ質問でも、サブ無しなら15ファイル分が残り、Exploreに委任すれば質問と要約の2行だけが残ります*

Exploreサブエージェントに任せると、メインに残るのは「質問」と「要約」だけになります。🔥 答えは同じなのに、コンテキストの消費がまるで違うんですよ！しかも、その要約を受け取った後のメインは、15ファイル分の雑音を抱えていないぶん、次の判断が濁りません。

### 最初から入っている3種類

自分で作らなくても、組み込みのサブエージェントが3つあります。

| 名前 | 役割 |
| --- | --- |
| General purpose | 探索と実行を組み合わせた、多段の仕事 |
| Explore | 高速な検索と、コードベースの中の移動 |
| Plan | Planモード中の調査 |

前回の記事のPlanモードの実験で、Claudeが頼んでもいないのに探索係を立ち上げていましたよね（図にも出しました）。あれがこの組み込みのサブエージェントだったんです！知らないうちに使っていました。

コースが挙げる利点は3つです。**仕事を焦点の絞れた単位に分割できる**、**メインのコンテキストを清潔に保てる**、**要約だけを持ち帰れる**。💡 3つとも「メインの作業記憶を守る」という一点に向いているのが分かりますよね。裏を返せば、メインの作業記憶を守る必要がない場面では、サブエージェントの出番も無いということです。🚀 この視点は4節でもう一度出てきます。

## 🛠️ 2. 作る：`/agents` と5つのフィールド

作り方は前回も触れましたが、今回はフィールドの意味まで押さえます。入口は `/agents` →「Create new agent」です。

![](/images/claude-code-subagents-course-japanese/figure04.png)
*/agents で聞かれる順番。スコープ、作り方、ツール、モデル、色の5つです*

聞かれる順番はこうです。

1. **スコープ**：Project-level（このリポジトリだけ）か、User-level（自分の全プロジェクト）か
2. **作り方**：手書きするか、Claudeに生成させるか。コースの推奨は **生成させる** です
3. **ツール**：Read-only（読むだけ）／Edit（編集）／Execution（実行）／MCP（Model Context Protocol／外部ツールを繋ぐ規格）／Other（その他）の分類から選びます
4. **モデル**：4択です（後述）
5. **色**：画面上で、どのサブエージェントが動いているかを見分けるためのものですね

ツールの選び方で、コースが例に挙げていたのがレビュアーです。レビューに編集は要らない。でも `git diff`（変更差分を表示するコマンド）を打つために、実行（Execution）は残す。💡 「何を渡さないか」から考える判断でした。まずは `/agents` を打って、Claudeに生成させてみて。手書きより早いし、生成されたものを直す方が、フィールドの意味が体で分かる。

モデルの4択はこうです。

| モデル | 特徴 |
| --- | --- |
| Haiku（ハイク） | 速くて軽い |
| Sonnet（ソネット） | 中間 |
| Opus（オーパス） | 複雑な分析向け |
| Inherit（継承） | メインと同じモデルを使う |

### できあがる設定ファイル

保存先は `.claude/agents/<name>.md` です。コースの例をそのまま載せますね。

```markdown:.claude/agents/code-quality-reviewer.md
---
name: code-quality-reviewer
description: Use this agent when you need to review recently written or modified code for quality, security, and best practice compliance.
tools: Bash, Glob, Grep, Read, WebFetch, WebSearch
model: sonnet
color: purple
---
You are an expert code reviewer specializing in quality assurance, security best practices, and adherence to project standards. ...
```

![](/images/claude-code-subagents-course-japanese/figure05.png)
*コースの例をそのまま解剖。フロントマターの5フィールドと、システムプロンプトになる本文です*

前回と同じで、YAML（ヤムル）フロントマター（先頭の設定部分）付きのMarkdownですね。フィールドは5つあります。

| フィールド | 意味 |
| --- | --- |
| `name` | 識別子。`@agent name` の形で直接呼ぶこともできる |
| `description`（ディスクリプション／いつ使うかの説明文） | いつ使うか。**1行で書くのが必須**。改行したいときは `\n` を使う。会話例を入れてもよい |
| `tools` | 使えるツールの一覧 |
| `model` | 上の4択 |
| `color` | 画面上の識別色 |

フロントマターの下の本文が、そのままシステムプロンプトになります。何に注目し、どう分析し、どう報告するか、をここに書くわけです。コースの例だと `tools` に Edit も Write も無いので、このレビュアーは指摘はできても直せません。✅ 設定ファイルを見た瞬間に「この助手は何ができないか」が分かるのが、いいところですね！

`description` の「1行必須」は、地味に罠だと思ったぜ。いつ使うかを丁寧に書こうとすると、どうしても長くなるじゃないですか。⚠️ でも改行を入れると壊れるので、`\n` で繋ぐ必要があるんです。

### 自動で使ってもらうには

作っただけでは、メインのClaudeが勝手に使ってくれるとは限りません。自分から使わせたいなら、`description` に **"proactively"（積極的に）** という言葉を入れます。「こういう場面ではこのエージェントを積極的に使え」という合図ですね！それから、`description` に入れる例が具体的であるほど、委任のタイミングが良くなります。「コードのレビューに使う」より「変更したばかりのコードの品質・安全性・規約違反を見るときに使う」の方が、メインは迷わず呼べるわけです。

テストの方法もコースは単純でした。何かコードを変えて、「レビューして」と頼む。レビュアーが使われなければ、`description` を直す。それだけです。🚀 設定ファイルを何時間も磨くより、1回呼ばれるかどうかを試した方が早いんですよね！

![](/images/claude-code-subagents-course-japanese/figure06.png)
*テストの一周。コードを変えて「レビューして」と頼み、使われなければ description を直します*

## 🔥 3. 効かせる4パターン

🔥 ここがこのコースの本体です！前回の記事で「作り方」は書いたんですが、「効かせ方」はまるで分かっていなかったんですよね。パターンは4つあります。

### パターン1：`description` は二役をこなす

💡 まず前提として、**全サブエージェントの `name` と `description` が、メインのシステムプロンプトに入る** んです。だからメインは、どんな助手がいて、それぞれ何が得意かを最初から知っています。

そのうえで、`description` が決めるのは「いつ起動するか」だけじゃないんですよ。**親が書く入力プロンプトの中身** も決めるんです。

![](/images/claude-code-subagents-course-japanese/figure07.png)
*description の二役。サブへの説明であると同時に、親が何を書いて渡すかを決める指示書でもあります*

コースの例が2つあります。レビュアーの `description` に「どのファイルをレビューしてほしいか、正確に伝えなければならない」と書いておくと、親はファイル名を列挙した具体的な依頼を書くようになります。Web検索係に「引用できる出典を返すこと」と書いておけば、親はそれを依頼に含めるようになる。`description` はサブへの説明であると同時に、**親への指示書** でもあるんですね。

1節で「サブが受け取るのは2つだけ」と書きました。そのうちの1つ、親が書くタスク説明の質を上げる手段が、実は `description` の中にあったわけです。サブの側を鍛えるのではなく、親が渡すものを鍛える。ここは発想が逆になっていて面白いところですね！

### パターン2：出力形式を決める（最重要）

✅ コースが「最も重要な改善」と言い切っていたのが、**出力形式の定義** です。効き目は2つ。**自然な停止点ができる** ことと、**走りすぎを防げる** ことです。

筋トレで「限界まで」と言われると、いつ止めていいか分からなくて逆に追い込めないですよね。「10回3セット」と決まっていれば、終わりが見えるから最後まで出し切れる。出力形式はそれと同じで、「この項目を埋めたら終わり」という区切りをサブに与えるんです。区切りが無いと、サブは足りない気がしてどこまでも調べ続けるか、逆に中途半端なところで手を止めるか、どちらかになります。

コースの例はレビュアー用で、6項目でした。

1. 要約
2. 致命的な問題
3. 重大な問題
4. 軽微な問題
5. 推奨事項
6. 承認ステータス

![](/images/claude-code-subagents-course-japanese/figure08.png)
*レビュアー用の出力形式6項目と、パターン3で足す7項目目。埋めたら終わり、という区切りになります*

問題を「致命的・重大・軽微」の3段に分けているのがポイントですね。「問題点を列挙して」だけだと、タイポと脆弱性が同じ行に並びます。段を切っておけば、受け取ったメインは上から順に見ればいい。要約を読む側の負担まで、出力形式で減らせるわけです。

### パターン3：障害を報告させる

そして、この6項目に **7番目** を足せ、というのがパターン3です。**「遭遇した障害」** の欄。サブが作業中に見つけた回避策、環境のクセ、必要だった特別なフラグ、問題を起こした依存関係。⚠️ こういうものを明示的に求めておかないと、サブは報告しないまま消えます。

すると何が起きるか。**メインが同じ罠を踏んで、同じ回避策をもう一度発見する** んです。トークン（文章を数える単位）と時間の無駄ですね。「サブの会話は捨てられる」という1節の話が、ここで効いてきます。捨てられる前に、書き残させないといけない。うちの裏方で、まさにこれが起きました（5節で白状します）。

出力形式の例を、7項目まで含めて書くとこうなります。

```markdown
## 出力形式
1. 要約
2. 致命的な問題
3. 重大な問題
4. 軽微な問題
5. 推奨事項
6. 承認ステータス
7. 遭遇した障害（見つけた回避策・環境のクセ・必要だった特別なフラグ・問題を起こした依存）
```

🚀 `description` を書いたら、次にこの7項目を本文の末尾に貼るのが早いです。効き目がいちばん早く出るのはここなので。

### パターン4：ツールを絞る

役割ごとに、渡すツールを削ります。コースの分け方はこうでした。

| 役割 | 渡すツール | 渡さないもの |
| --- | --- | --- |
| 調査係 | Glob（グロブ／パターンでファイル名を探す）、Grep（グレップ／中身を文字列検索する）、Read | 書く・実行する系は一切なし |
| レビュアー | 上の3つ + Bash（バッシュ／シェルコマンドの実行。`git diff` 用） | Edit、Write |
| コード変更係 | Edit、Write を含む | ―― |

![](/images/claude-code-subagents-course-japanese/figure09.png)
*役割ごとのツールの持ち物。調査係、レビュアー、コード変更係の順に増えていきます*

Edit と Write を持つのは、コード変更係だけです。レビュアーは指摘はできるけど直せない。調査係は読むしかできない。役割が「できること」ではなく「できないこと」で定義されているのが分かりますよね。渡すツールが少ないほど、サブが脱線する余地も減ります。調査を頼んだつもりの助手が、勝手にファイルを書き換えていた、という事故が構造的に起きなくなるんです！

### 4パターンを一枚で

| パターン | 何を書くか | 何が良くなるか |
| --- | --- | --- |
| 1. 具体的な `description` | いつ使うか + 呼ぶ側が渡すべきもの | 起動のタイミングと、親が書く依頼の質 |
| 2. 構造化された出力 | 埋めるべき項目の一覧 | 自然な停止点。走りすぎの防止 |
| 3. 障害の報告 | 出力の末尾に「遭遇した障害」欄 | メインが同じ罠を再発見しなくなる |
| 4. 絞ったツール | 役割に必要な最小限 | 脱線と事故の予防 |

4つとも、書く場所は設定ファイル1枚の中です。フロントマターに1と4、本文の末尾に2と3。次の節では、これを踏まえて「そもそも使うべきか」を判断します。

## ⚖️ 4. 使う場面・避ける場面

ここが一番、意見が割れそうな節ですね。コースは「サブエージェントを使え」だけでなく、「使うな」の方も同じくらい丁寧に書いていました。

### 判断は一問だけ

🤔 **途中の作業は重要か？**

「いいえ」なら委任する。「はい」ならメインに置く。これだけなんです！結果だけ欲しいなら渡す。途中を見ながら自分が反応したいなら、手元に置く。1節の「どう結論に至ったかが見えなくなる」代償を、払っていい仕事かどうか、と言い換えてもいいですね。

![](/images/claude-code-subagents-course-japanese/figure10.png)
*判断は「途中の作業は重要か？」の一問だけ。いいえなら委任、はいならメインに置きます*

向いている場面として、コースは3つ挙げています。

- **結果だけが欲しい**
- **探索がメインを散らかす**
- **新鮮な視点、あるいはカスタムシステムプロンプトが効く**

順番に、コースの例で見ていきますね。

### 向く例1：調査

「JWT（JSON Web Token／ログイン状態を証明する署名付きの文字列）の検証はどこでやっている？」という調査です。サブが返してくる要約は、この1文でした。

> JWT validation happens in middleware/auth.js line 42, called from the Express router in route/api.js

「JWTの検証は middleware/auth.js の42行目で、route/api.js のExpress（エクスプレス／Node.jsのWebフレームワーク）ルーターから呼ばれている」。これだけ分かれば次に進めますよね。辿った過程は要らない。何十ファイルを開いたかも要らない。✅ 「途中の作業は重要か」に「いいえ」と即答できる典型です。

### 向く例2：コードレビュー

ここ、面白かったんですよ！🔥 **Claudeは「他人が書いたコード」として提示された方が、よくレビューできる** そうなんです。自分が何ターンもかけて作ったものは、新しい目で見られない。人間と同じですね。だから別のコンテキストで `git diff` を読ませて、プロジェクト固有の基準はシステムプロンプトに書いておく。前回の記事で「コミット前に新しい目」と書いた話の、理屈の部分がこれでした。

![](/images/claude-code-subagents-course-japanese/figure11.png)
*同じ diff でも、作った本人より初めて見る係の方が指摘が出ます。新しい目の理屈です*

### 向く例3：カスタムシステムプロンプトが効く仕事

コースの例が2つあって、これが5節で自分がそのまま実装するものになります。

**コピーライティング用**。口調、読者、文体をシステムプロンプトに持たせます。Claudeの既定の声は「簡潔な技術文書」なので、LP（ランディングページ／広告から飛んでくる1枚の紹介ページ）やメール配信の文章には向かないんですね。だから専用の声を持つ係を作る。メインに毎回「この口調で」と頼むより、最初からその声で起動する助手を用意する方が、ブレません。

**スタイリング用**。デザインシステムのファイルをシステムプロンプトで指し示しておくと、起動時にそれが読み込まれます。色の変数、余白、部品のパターンを知った状態でCSS（スタイルシート／見た目を決める記述）を書けるわけです。💡 「まずこのファイルを読んで」を毎回言わなくていい、というのが地味に効きます。

### 避ける3つ（アンチパターン）

![](/images/claude-code-subagents-course-japanese/figure12.png)
*コースが名指しで避けろと言った3つ。専門家の肩書き、直列パイプライン、テスト実行係です*

**1. 専門家を名乗らせる**。「あなたはPythonの専門家です」は価値ゼロだそうです。Claudeは既にPythonを知っているから。背番号10をつけても足は速くならないのと同じで、肩書きは能力を増やさないんですよ！サブエージェントが効くのは「文脈を分ける」ときであって、「役を演じさせる」ときじゃない。専門家の肩書き、今日で卒業して。

**2. 直列パイプライン**。再現係→デバッグ係→修正係、と繋ぐやつです。バグ修正のように各ステップが前のステップに依存する仕事だと、受け渡しのたびに情報が落ちます。再現係が気づいた細かい条件が、要約で削られてデバッグ係に届かない。1節の「途中が見えなくなる」代償が、直列にすると受け渡しの回数ぶん積み重なるわけですね。

**3. テスト実行係**。「テストが失敗しました」だけ返してきて、どのテストがどう失敗したかの詳細が隠れてしまう。コースによると、検証した全構成の中で **最も成績が悪かった** そうです。テスト係が最下位、は二度見した。でも考えてみれば当然で、テストの結果こそ「途中の作業が重要」な典型なんですよね。要約されたら困る情報を、要約する係に渡していたわけです。

⚠️ 3つとも、結局は最初の一問に戻ります。途中の作業は重要か。バグ修正もテストも「はい」なんですよ。

## 🧪 5. やってみた：表と裏に分けて記事を書く

前回の記事を書いたときから、実は既に使っていました。今回のコースで「なぜ効いたか」と「なぜ止まったか」の両方が分かったので、時系列で書きますね。

### 表と裏

前作を書くとき、学習する「表」のセッションと、画像を作る「裏」のサブエージェントに分けました。裏に渡したのは「この節に、こういう図を作って入れて」という依頼文だけ。返ってきたのは「何を作ってどこに入れたか」の要約だけでした。1節で説明した仕組みそのままです。✅ 表のコンテキストは、画像生成の何十回ものツール呼び出しで汚れませんでした。

![](/images/claude-code-subagents-course-japanese/figure13.png)
*学習する表と画像を作る裏。行き来するのは依頼文と要約だけです*

このときは「うまくいった」としか思っていなかったんですが、4節の一問に当てはめると、画像づくりは「結果だけが欲しい」仕事で、しかも「探索がメインを散らかす」仕事でもある。委任して正解だったわけですね。

### 裏が止まった話

うまくいった話だけだと嘘になるので、失敗も書きます。⚠️ 裏の画像係が、画像生成の「生成待ち」で何度も止まったんです。3回。都度「最後までやれ」と再指示して、ようやく完了しました。

原因は、コースを受けて分かりました。**完了条件、つまり出力形式を渡していなかった** んです。3節のパターン2ですね。「何を埋めたら終わりか」が無いから、裏は途中で自然に手を止めていた。区切りが無い作業に、区切りが無いまま送り出していたわけです。

もうひとつ。裏は「レート制限（一定時間に呼べる回数の上限）で並列5本は無理、2レーン直列が正解」という回避策を、**自発的に** 報告してくれました。おかげで次の回から活かせたんですが、これは運が良かっただけなんですよね。最初から「遭遇した障害」の欄を求めておくべきだった。パターン3です。3回も再指示しておいて、原因が自分側にあるとは、コースを読むまで思っていなかった。裏が悪いんじゃなくて、自分の設計ミスだったんです。

![](/images/claude-code-subagents-course-japanese/figure14.png)
*裏が止まった原因の分解。出力形式が無いから停止点が無く、障害欄が無いから報告が運任せでした*

### 校正は別の目

統合した記事を、「読み取り専用の校正係」サブエージェントに読ませました。すると、本文に存在しない参照を引用している箇所、数字の矛盾、画像の中に残った古い文言。書いた本人（メイン）が完全に見落としていた致命的なミスを、いくつも拾ってきたんです！

4節のコードレビューと同じ理屈ですね。何ターンもかけて統合したメインには、もう「初めて読む目」が無い。🔥 別のコンテキストで、記事を初めて渡された助手の方が、よく見えていた。自分の書いたもの、一回別の目に通してみて。自分が見落としているものの量に、ちょっとへこむから。

![](/images/claude-code-subagents-course-japanese/figure15.png)
*読み取り専用の校正係が拾った3種のミス。存在しない参照、数字の矛盾、画像内の古い文言です*

### コースの2例を、そのまま実装した

4節の「コピーライティング用」と「スタイリング用」を、そのまま `~/.claude/agents/` に作りました。

**`zenn-copywriter`**：口調・読者・文体を持つコピーライター係です。ツールは Read、Edit、Write、Grep、Glob。Bash は渡していません。文章を書く係にシェルは要らないので、パターン4のとおり削りました。

**`zenn-card-stylist`**：図解係です。起動時にデザインシステムのCSSとマスコットのREADMEを読むように、システムプロンプトで指し示しています。コースの「スタイリング用」の例そのままですね。

両方に、3節の出力形式と「遭遇した障害」欄を入れました。そして `description` には、**呼ぶ側が必ず渡すもの** を明記しています。パターン1の「`description` は親への指示書でもある」を、そのまま使ったわけです。

```yaml
name: zenn-copywriter
description: Zenn記事の本文を、書き手の声(です・ます基調+馴れ馴れしい話しかけ+くだけた独り言+たまにタメ語)で書く・書き直すときに使う。(中略)呼び出す側は必ず (1) 対象ファイルの絶対パス (2) 作業の種類 (3) 目標の文字数 (4) 変えてはいけない範囲 (5) 元になる事実・素材の場所、を入力プロンプトに書くこと。
tools: Read, Edit, Write, Grep, Glob
model: inherit
```

![](/images/claude-code-subagents-course-japanese/figure16.png)
*zenn-copywriter の設定。description の後半に「呼ぶ側が必ず渡す5つ」を書いています*

`description` の後半を見てください。「呼び出す側は必ず (1)〜(5) を書くこと」。これが入っているおかげで、メインがこの係を呼ぶとき、対象のパスや文字数や触ってはいけない範囲を、自分から依頼文に書くようになりました。サブの側は何も変えていないのに、届く依頼の質が上がったんです！

図解係の方には、「最初に必ず読むもの」という節と、「既知のハマりどころ」という節を作りました。後者の中身は3つ。**レート制限は並列2まで**、**生成待ちで止まらない**、**素材は消えない場所へ**。さっきの失敗が、そのまま3行になっています。裏が自発的に報告してくれた回避策を、次からは最初から知っている状態で起動させる、ということですね。💡 サブの会話は捨てられるので、学びは設定ファイルに書き戻さない限り残らないんです。

そして白状すると、**この記事を書いているのは、そのコピーライター係です**！表のセッションが裏取りした事実をブリーフにして渡し、この係が本文を書いています。4節の「既定の声は簡潔な技術文書」という話を、自分の記事で確かめている最中なわけですね。

### 口調の調整は、メインでやった

一方で、前回の記事では、サブエージェントに投げ切らなかった仕事もあります。口調の調整です。「〜だぜ」が多すぎないか、タメ語の頻度はこのくらいでいいか。これは好みを見ながら、その場で反応する必要がある仕事なんですよね。だからメインでサンプルを見せて、承認を取ってから公開しました。

4節の一問で言えば、「途中の作業は重要か？」に「はい」と答えた実例です。結果だけ受け取っても判断できない仕事は、手元に置く。

![](/images/claude-code-subagents-course-japanese/figure17.png)
*やったことを一問で振り分けた結果。委任したのは3つ、手元に置いたのは口調の調整だけです*

| やったこと | 委任した？ | 一問への答え |
| --- | --- | --- |
| 画像を作る | した | 途中は要らない |
| 記事を校正する | した | 新しい目が要る |
| 本文を書く | した | 専用の声が要る |
| 口調を決める | しなかった | 途中の反応が要る |

## 🎓 6. 授業に持っていく話

自分は大学院でAIエージェントを研究していて、10月に学生向けに「マルチエージェントでチームを組む」授業を担当します。このコースで、授業の山場が決まりました！

学生に「エージェントでチームを組んで」と言うと、まず間違いなく、PM・設計・実装・テストの「専門家」を並べて、直列に繋ぎたくなるんです。会社の組織図をそのまま写すのが一番自然ですから。でもコースは、それを名指しでアンチパターンと言っている。専門家を名乗らせても能力は増えないし、直列は受け渡しで情報が落ちる。しかも「テスト係」は、検証で最下位だった。⚠️ 学生が最初に組みたくなる形が、そっくりそのまま「やるな」の3つに当たるんですよ！

![](/images/claude-code-subagents-course-japanese/figure18.png)
*学生が最初に組みたくなる直列チームと、コースが勧める「窓で分ける」形の対比です*

じゃあ何で分けるのか。前回の記事で「役割分担はコンテキストの分離である」と書きました。💡 今回はその続きで、**何を共有しないかを先に決める**、そして **分けた先には出力形式と障害欄で「持ち帰り方」を決めておく**、まで言えるようになりました。✅ 「役」ではなく「窓」で分ける。授業の山場、ここに決めた。

## 🎯 7. まとめ：持ち帰る4つと、次のコース

✅ 4レッスンから持ち帰るのは、この4つです！

1. **サブは要約しか返さない。だから途中が要る仕事は渡さない**。判断は「途中の作業は重要か？」の一問だけ
2. **`description` は親への指示書でもある**。呼ぶ側が渡すべきものを、そこに書いておく
3. **出力形式が停止点になる**。埋める項目を決めて、末尾に「遭遇した障害」欄を足す
4. **専門家の肩書き、直列パイプライン、テスト実行係は避ける**。能力は増えず、情報は落ち、詳細は隠れる

![](/images/claude-code-subagents-course-japanese/figure19.png)
*4レッスンから持ち帰る4つ。まずは設定ファイルの末尾に出力形式と障害欄があるかを確かめてみてください*

🔥 サブエージェントを1体でも作ったことがあるなら、設定ファイルを開いて、出力形式と障害欄が末尾にあるか確かめてみて。無ければ、まずそこから。
