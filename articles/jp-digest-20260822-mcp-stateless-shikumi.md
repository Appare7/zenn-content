MCP（Model Context Protocol、モデルコンテキストプロトコル）の新仕様 `2026-07-28`、自分でサーバーを作っている人ほど「え、うちの実装そのまま動くの？」となるやつです。  
この記事では、複数の海外記事と公式発表を突き合わせつつ、日本の開発者が気になりそうな順に組み直して見ていきます。  
結論から言うと、今回の主役は「ステートレス（状態を持たない）化」です。ここを見落とすと、地味にハマります。

## セッションが消えた、という一行に全部詰まってる

2026年7月28日、MCPの新しい仕様バージョン `2026-07-28` が現行仕様として公開されました。  
公式ブログを書いたのは、リードメンテナの David Soria Parra と Den Delimarsky です。

MCPのバージョンは、日付そのものが版番号になっています。

- `2024-11-05`
- `2025-03-26`
- `2025-06-18`
- `2025-11-25`
- `2026-07-28`

今回のいちばん大きな変化は、公式の言い方を借りると、MCPが「双方向のステートフルなプロトコル」から「リクエスト/レスポンス型のステートレスなプロトコル」へ変わったことです。

つまり、ざっくり言うとこうです。

**サーバー側でセッションを握り続ける前提を、やめた。**

ここ、かなり大きいです。  
`initialize` して、セッションIDを持って、その接続の上でやり取りして……という世界から、毎回のリクエストだけで必要な情報を渡す世界に寄っています。

しかも、もう小さな実験規格ではありません。公式ブログの数字では、主要4つの SDK（ソフトウェア開発キット）の合計で月あたり5億弱のダウンロード。TypeScript版とPython版は、それぞれ累計10億ダウンロードを超えています。早すぎません？

この `2026-07-28` のリリース候補（正式版になる前の候補版）は、2026年5月21日に出ていました。その時点で「ローンチ以来最大の改訂」と説明されていたので、今回の変更幅はかなり大きめです。

## 何が入れ替わったのか、6つだけ押さえる

細かい変更はたくさんありますが、まずはこのあたりを押さえると全体像が見えます。

### 1. `initialize` / `initialized` がなくなった

接続開始時の握手だった `initialize` / `initialized` が廃止されました。  
「最初に必ずこれを投げて、サーバーと状態を合わせる」という入り口がなくなったわけです。

### 2. `Mcp-Session-Id` もなくなった

セッションIDを表す `Mcp-Session-Id` ヘッダーも廃止です。  
これまで「この会話はこのサーバーインスタンスに紐づいている」という前提で作っていた場合、ここが直撃します。

### 3. 毎回の `_meta` に情報を載せる

かわりに、プロトコルのバージョン、クライアントの素性、能力の情報は、毎回のリクエストの `_meta` に載せて送ります。

状態をサーバーに覚えさせるのではなく、リクエストの中に持たせる。  
今回の変更は、かなりの部分がこの一言に集約されます。

さらに `_meta` には、W3C Trace Context（分散トレースの標準）の `traceparent` / `tracestate` / `baggage` も載せられます。  
SDKやゲートウェイ（入口で通信を受ける中継役）をまたいで追跡しやすくなるのは、運用している人にはうれしいところです。ここ、地味に効きます。

### 4. 能力確認は `server/discover`

サーバーの能力を先に知りたいときは、新しい `server/discover` という RPC（遠隔手続き呼び出し）を叩きます。

毎回ぜんぶ確認するのではなく、必要なときだけ聞く形です。  
これも「つなぎっぱなしで状態を共有する」前提から離れるための部品ですね。

### 5. `Mcp-Method` / `Mcp-Name` ヘッダーが入った

Streamable HTTP（ストリーミング可能なHTTP）のリクエストには、`Mcp-Method` と `Mcp-Name` という2つのヘッダーが付くようになりました。

これで、ゲートウェイやロードバランサ（負荷分散装置）が、JSON本文を読まずに振り分けや計測をできます。詳しくは後ろのセクションで。

### 6. `ttlMs` / `cacheScope` と MRTR

ツールや資源の一覧を返す応答に、`ttlMs` と `cacheScope` というキャッシュの指定が付くようになりました。これも後ろで詳しく見ます。

それから、MRTR（Multi Round-Trip Requests、複数往復リクエスト）も大事です。  
サーバーが処理の途中でユーザーに聞き返したいときのやり方が変わりました。後で詳しく見ます。

## スティッキーセッションという名の足かせが外れた

今回のステートレス化で何がうれしいのか。  
クラウド事業者側の解説では、従来のセッション固定方式が抱えていた問題として、主に4つが挙げられています。

### 負荷分散しづらかった

セッションが特定のコンテナに紐づくと、普通のラウンドロビン（順番に振り分ける方式）ではうまく配れません。

たとえば、1回目のリクエストを受けたコンテナがセッション状態を持っているなら、2回目も同じコンテナに行かないと困りますよね。  
でもそれ、ロードバランサから見るとけっこう面倒です。

### セッションアフィニティが必要だった

そこで必要になるのが、セッションアフィニティ（同じサーバーに貼り付ける設定）です。  
いわゆるスティッキールーティングですね。

ただ、これを入れるとトラフィックが偏りやすくなります。  
偏ると、オートスケール（負荷に応じた自動増減）もきれいに効きにくい。クラウドで水平に伸ばしたいのに、足元に重りを付けて走っている感じです。

### Podが落ちるとセッションも消えた

Pod（実行単位）が落ちた瞬間、そのPodが持っていたセッションも消えます。  
すると利用者側にはエラーが出ます。

もちろん、落ちないように作るのも大事です。  
でもクラウド上では、個々の実行単位が入れ替わること自体はわりと普通に起きます。そこにセッションを強く結びつけると、どうしても弱くなります。

### 共有ストアや中身を覗くゲートウェイが必要だった

リモートのMCPサーバーでは、共有Redisのようなストアを持つか、ゲートウェイでパケットの中身を覗く必要がありました。

これもつらいです。  
共有ストアを足せば構成が増えますし、ゲートウェイがJSON本文まで読むなら、レイテンシ（遅延）や運用コストも増えます。

クラウド側の解説では、従来のステートフルな形は「モダンなクラウドネイティブのスケーラビリティの核心を壊していた」とまで書かれています。なかなか強い言い方です。

ただし、具体的にレイテンシが何%改善した、みたいな性能数値はこの解説には出ていません。  
なので、ここでは「速くなった」とは書きません。正確には「普通のクラウド構成で運用しやすくなった」です。

結果として、新仕様のMCPサーバーは、共有ストレージなしで、ごく普通のラウンドロビンのロードバランサの後ろに置きやすくなりました。

## サーバーが「聞き返す」のをやめた話（MRTR）

ここも大きな変更です。

これまで、サーバーが処理の途中でユーザーに聞きたいことが出たときは、接続を開いたまま「サーバーから」問い合わせを送っていました。  
対象になるのは、elicitation（ユーザーへの追加質問）や sampling（サーバーがクライアント側のモデルを呼ぶ機能）、roots（作業ディレクトリの範囲を伝える機能）です。

でも新仕様では、そのやり方をやめます。  
かわりに MRTR（Multi Round-Trip Requests、複数往復リクエスト）を使います。

流れはこうです。

### 1. クライアントがツールを呼ぶ

まず、いつも通りクライアントがツールを呼びます。  
たとえばファイル削除ツールを呼ぶ、みたいな場面です。

### 2. サーバーはいったん `input_required` を返す

サーバーは、接続を握ったまま待ちません。

かわりに、`resultType: "input_required"` という結果を返します。  
そこには、聞きたいことを入れる `inputRequests` と、途中経過を詰めた `requestState` を入れます。

公式の説明にある例のイメージでは、たとえばこんな確認です。

**「ファイルを3件消していい？」**

これを、真偽値のスキーマ付きで返します。  
「はい / いいえ」をユーザーに聞いてね、というわけです。

### 3. クライアントがユーザーに聞いて、もう一度送る

クライアントはユーザーに確認します。  
その答えを `inputResponses` に入れ、さっき受け取った `requestState` をそのまま添えて、同じ呼び出しをもう一度送ります。

この「`requestState` をそのまま返す」がポイントです。  
サーバー側のメモリに続きを置いておくのではなく、続きに必要な文脈をペイロード（送信データ本体）に持たせています。

### 4. どのインスタンスが受けても続けられる

続きに必要な情報は全部リクエストの中にあります。  
なので、2回目のリクエストを別のサーバーインスタンスが受けても処理できます。

これがMRTRの肝です。  
つなぎっぱなしの双方向ストリームが要らなくなる。サーバーが「待ってるからあとで返事して」ではなく、「必要な情報を返すから、答えを持ってもう一回来て」という形に変わったんです。

## ヘッダーとキャッシュ：地味だけど運用が変わるところ

ステートレス化の話に比べると地味に見えますが、`Mcp-Method` / `Mcp-Name` とキャッシュ指定もかなり実務寄りの変更です。

### JSON本文を読まずに振り分けられる

Streamable HTTPのリクエストには、次の2つのヘッダーを付けます。

- `Mcp-Method`: 操作名。例: `tools/call`
- `Mcp-Name`: 対象名。例: `search`

これにより、ゲートウェイやロードバランサはJSON本文を読まなくても、どの操作か、どのツールかを見られます。

たとえば「`tools/call` の `search` だけ別の経路に流す」とか、「ツールごとに計測する」といったことが、ヘッダーだけでやりやすくなります。  
本文を開けずに済むのは、けっこうありがたいです。

ただし、なりすまし対策も入っています。  
ヘッダーと本文の中身が食い違うリクエストは、サーバーが拒否しなければなりません。

ヘッダーに `Mcp-Name: search` と書いてあるのに、本文では別のツールを呼んでいる、みたいなリクエストは弾く必要があります。ここを雑にすると危ないです。

### 一覧結果にキャッシュの寿命が付く

`tools/list` / `prompts/list` / `resources/list` / `resources/read` の応答には、`ttlMs` と `cacheScope` が付きます。

- `ttlMs`: この結果が何ミリ秒のあいだ新鮮か
- `cacheScope`: ユーザー間で使い回していいか

HTTPの `Cache-Control`（キャッシュ制御）の考え方を、そのままMCPの応答に持ち込んだ形です。

さらに、一覧の並び順が決定的、つまり毎回同じ条件なら同じ順番になります。  
これによって、上流のプロンプトキャッシュも安定して効きやすくなります。

そしてもうひとつ大事なのが、一覧が変わったかどうかを知るために、つなぎっぱなしのストリームを維持しなくてよくなることです。  
キャッシュの寿命が明示されるだけで、運用の見通しがかなりよくなります。

## 認可とタスクと画面：まわりも同時に動いた

今回の変更はステートレス化だけではありません。  
認可、長時間タスク、画面表示の拡張まわりも同時に動いています。

### 認可まわりは締め直し

認可では、いくつかの要件が強くなっています。

- 発行元、つまり issuer（トークンを発行した主体）の検証が RFC 9207 に沿って必須になった
- Dynamic Client Registration（動的クライアント登録、DCR）のときに `application_type` を指定する
- クライアントの資格情報は、それを発行した認可サーバーに紐づけられる
- DCRそのものが正式に非推奨になり、CIMD（クライアントID メタデータ文書）が推される
- 企業向けに Enterprise Managed Authorization（企業管理型の認可）という拡張ができた

DCRは後方互換のため当面は動きます。  
ただし、将来の版で削除される流れです。新しく設計するなら、CIMDを見ておくのが自然です。

OAuth（認可の仕組み）/ OIDC（OpenID Connect、認証情報の連携仕様）まわりを自前で実装している人は、ここを後回しにするとあとでつらくなりそうです。

### 拡張の仕組みが正式化された

「拡張（extensions）」の仕組みも正式化されました。

拡張は、逆DNS形式の識別子を持ちます。  
そして、MCP本体とは別にバージョンが進みます。

本体に全部詰め込むのではなく、必要な機能を拡張として切り出して育てていく形ですね。

### Tasks は拡張へ引っ越し

Tasks（長時間かかる処理の扱い）は、実験的な本体機能から `io.modelcontextprotocol/tasks` という拡張に移りました。

そこには、ポーリング方式の `tasks/get` と、新しい `tasks/update` があります。  
変更通知は `subscriptions/listen` という単一のストリームにまとめられました。

長時間ジョブを扱っているサーバーは、この移動を見逃さないほうがいいです。

### MCP Apps はチャット内に画面を出せる

MCP Apps は、サーバー側が定義した HTML（画面を記述する言語）/ JS（JavaScript、ブラウザで動くプログラム）の画面を、サンドボックス化された iframe（隔離された枠）の中でチャット内に表示できる拡張です。

クライアント側でUIを作り込まなくても、ダッシュボードや設定ウィザードを出せます。  
2026年1月26日に最初の公式拡張として先に出ていたものが、今回の拡張フレームワークに取り込まれました。

## 廃止リストと「最低12か月」の時計

今回、いくつかの機能が非推奨になりました。  
すぐ消えるわけではありません。正式な廃止ポリシーとして「最低12か月」の猶予があります。

非推奨になったのは、主にこのあたりです。

- Roots（作業ディレクトリの範囲をサーバーに伝える機能）
- Sampling（サーバーがクライアント側のモデルを呼ぶ機能）
- Logging（プロトコル層のログ通知）
- 旧来の HTTP+SSE トランスポート（HTTPとServer-Sent Eventsを使う通信方式）
- Dynamic Client Registration（動的クライアント登録、DCR）

移行先としては、次のものが挙げられています。

- Roots → 引数やサーバー設定でパスを渡す
- Sampling → サーバー側から LLM（大規模言語モデル）の API（外部機能を呼ぶ窓口）を直接呼ぶ
- Logging → `stderr`（標準エラー出力）や OpenTelemetry（観測データを扱うための仕組み）
- 動的クライアント登録 → CIMD
- HTTP+SSE → Streamable HTTP

ここで気をつけたいのは日付の言い方です。

公式が明言しているのは「最低12か月」という条件です。  
一方で、12か月の起点を `2026-07-28` として、`2027年7月28日` を目安に挙げている解説記事もあります。

なので、「2027年7月28日に必ず消える」と断定するのは避けたほうがよさそうです。  
ただ、時計はもう動き出しています。当面は動くけれど、依存しているなら洗い出しは早めに始めたいところです。

## ここまでの2年弱を1枚で

MCPは、ここ2年弱でかなり速いペースで変わってきました。  
ざっと流れを見ておくと、今回のステートレス化が突然出てきた話ではないことがわかります。

- 2024-11-05: 初版の仕様。クライアント/サーバー構成、JSON-RPC 2.0、`tools` / `resources` / `prompts`、`stdio` と HTTP+SSE
- 2025-03-26: OAuth 2.1 ベースの認可、Streamable HTTP が HTTP+SSE を置き換え
- 2025-06-18: 構造化されたツール出力、elicitation、MCPサーバーをOAuthのリソースサーバーとして位置づけ
- 2025-11-25: OpenID Connect Discovery、アイコンのメタデータ、samplingでのツール呼び出し、CIMD、実験的なTasks、JSON Schema 2020-12を既定の方言に
- 2025-12-09: MCPが Linux Foundation 傘下に新設された Agentic AI Foundation（AAIF）に寄贈
- 2026-01-26: MCP Apps が最初の公式拡張として提供開始
- 2026-05-21: `2026-07-28` のリリース候補が公開
- 2026-06-29: リリース候補に対応したベータSDKが公開
- 2026-07-28: 正式版として公開。4つのTier 1（第一級）SDKが同日に対応

2025年12月9日の寄贈も大きな節目です。  
MCPは Linux Foundation 傘下に新設された Agentic AI Foundation（AAIF）に寄贈されました。AAIFは Anthropic、Block、OpenAI が共同で設立しています。

統治のしくみ自体は変わらないとされましたが、「一社の仕様」から「業界の共通規格」へ寄っていく流れの上に、今回の大きな改訂があるわけです。

## で、自分は何をすればいい？

ここからがいちばん大事ですね。  
自分のMCPサーバーやクライアント、ホストをどう見直せばいいのか。

### サーバーを作っている人

まずサーバー側です。

- `initialize` を必須の入り口にするのをやめる
- セッションごとに持っていた状態を外に出す
  - 外部ストレージに置く
  - あるいは、そもそも状態を持たない設計にする
- `Mcp-Method` ヘッダーでの振り分けに対応する
- `tools/list` の応答に `ttlMs` を付ける
- ツールの入力スキーマを JSON Schema 2020-12 に厳密に沿わせる
- Roots / Sampling / Logging に依存している箇所を洗い出して置き換える
- OAuth / OIDC のトークン検証・発行元検証を強くする

特に注意したいのが JSON Schema 2020-12 です。  
今までゆるい書き方で通っていたスキーマが、弾かれる可能性があります。

「動いてるから大丈夫」と思っていたツール定義が、新しいSDKやクライアントでは急に失敗する。ありそうで怖いやつです。  
ここはテストを厚めに見たいところです。

### クライアントやホストを作っている人

クライアントやホスト側では、次を見ます。

- 起動時に必ず `initialize` を送るのをやめる
- 複数インスタンスにまたがるステートレスな経路を前提に設計する
- `ttlMs` のキャッシュ指示を尊重する
- 認証フローを新しい要件に合わせる
- 非推奨機能の置き換え先を用意しておく

クライアント側も、「このサーバーとは最初に握手して、同じセッションで進む」という思い込みを外す必要があります。  
サーバーが毎回違うインスタンスでも成立する、という前提で考える感じです。

### SDKはどこまで来ている？

SDKの状況も見ておきます。

Tier 1（第一級）SDKとされる TypeScript / Python / Go / C# の4つは、`2026-07-28` に対応済みです。Rust版はベータです。

2026年6月29日には、リリース候補に対応したベータSDKも公開されていました。  
Python版はv2、TypeScript版もv2で用途ごとのパッケージに分割され、GoとC#もベータが並びました。

クラウド事業者の解説では、ベータの入れ方の例として次が示されています。

```bash
pip install "mcp[cli]==2.0.0b1"
```

また、TypeScript側には codemod（コードを自動書き換えするツール）もあると書かれています。  
大きめの移行では、こういう道具があるだけでだいぶ気が楽になりますね。

もちろん、最低12か月の猶予はあります。  
今すぐ全部を一晩で直す必要はありません。

ただし、新しく作るMCPサーバーなら、もう新仕様で作るのがいちばん素直です。  
古いセッション前提で作ってから移行するのは、二度手間になりやすいです。

## まとめ：MCPが「ふつうのWebサービス」になった日

今回の `2026-07-28` は、MCPが「つなぎっぱなしの特別な接続」から「ふつうのHTTPリクエスト」に近づいた更新です。  
サーバーに状態を抱え込ませず、リクエストの中に文脈を入れて運ぶ。これだけで、ロードバランサの後ろに置くときの気持ちよさがかなり変わります。

もちろん、既存実装には痛いところもあります。`initialize`、セッションID、Roots、Sampling、Loggingに寄せて作っていたなら、ちゃんと見直しが必要です。  
でも方向性はかなりわかりやすいです。MCPサーバーを、より「ふつうのWebサービス」として作れるようにする。そのための大きな一歩、というわけです。
