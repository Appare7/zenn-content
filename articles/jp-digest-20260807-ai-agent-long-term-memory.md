AIエージェントを作ると、だいたい最初にぶつかるのが「セッションが変わると全部忘れる」問題ですよね。  
2026年のいま、この解き方はかなり形になってきました。専用ベンチマークがあり、専用のOSS（オープンソースソフトウェア）があり、思想の違う3つの実装方式があります。  
この記事は、海外の技術ブログ、フレームワーク公式の発表、査読論文をいくつか突き合わせて、日本語で読みやすく組み直したものです。  
先に結論を言うと、いちばん難しいのは「覚えること」じゃなくて「古くなった記憶を捨てること」なんです。

![AIエージェントの長期記憶：覚えることより忘れることが難しい](/images/jp-digest-20260807-ai-agent-long-term-memory/figure1.png)

## 「記憶」がエージェント設計の一級市民になった

2026年時点で、エージェントの記憶、つまりメモリは「あとから足す便利機能」ではなく、独立した設計テーマになっています。専用ベンチマークが複数あり、専用のOSSとベンダーも揃ってきました。

GitHub のスター数を見ると、困っていた人の多さがわりと素直に出ています。2026年8月7日時点、GitHub API で実測された数字です。

| リポジトリ | スター数 |
|---|---:|
| mem0ai/mem0 | 62,694 |
| topoteretes/cognee | 29,831 |
| getzep/graphiti（Zep のエンジン） | 29,630 |
| letta-ai/letta | 24,123 |

「みんな忘れんぼエージェントに悩んでたんだな……」という感じですよね。

Letta のルーツは、2023年10月の MemGPT という研究です。LLM（大規模言語モデル）を「メモリ容量が限られたOS（基本ソフト）の上で動くプロセス」と捉える発想から始まりました。要するに、AIにもページングっぽいメモリ管理をさせよう、というわけです。その後、汎用のエージェント基盤に育つ過程で Letta に名前が変わりました。

記憶レイヤーは、LangChain / LangGraph / LlamaIndex / CrewAI / AutoGen といった主要なエージェントフレームワークに組み込んで使う前提になっています。Mem0 だけでも、13のフレームワーク連携と20のベクトルストア対応が文書化されています。もう「自作のメモ配列でがんばる」段階ではなくなってきたんです。

## そもそも長期記憶って、中で何をやってるの？

![長期記憶の4つの仕事（保存・整理・検索・寿命管理）](/images/jp-digest-20260807-ai-agent-long-term-memory/figure2.png)

記憶システムの仕事は、大きく4つに分けられます。

1. 保存（Storage）  
   どこに置くか、どう索引を張るか。

2. 整理（Curation）  
   矛盾する情報や、古くなった情報の始末をつける。

3. 検索（Retrieval）  
   「文字面が似てるだけ」ではなく、「本当に関係のある」記憶を返す。

4. 寿命管理（Lifecycle）  
   統合する、重要度を上げる、下げる、引退させる。

で、みんなが力を入れてるのは1と3なんですよね。保存と検索です。たしかにここは派手です。ベクトル検索だとか、ハイブリッド検索だとか、いかにも作ってる感があります。

でも実際にハマるのは、2と4のほうです。本棚に本を突っ込むのは簡単なんです。難しいのは、もう読まない本を捨てる判断のほう。AIエージェントの記憶も同じで、「どこに入れるか」より「いつ古いと見なすか」のほうがずっと厄介です。

## 数字で見る：ベンチマーク3つと、正直な限界

![記憶ベンチマーク3種の規模とスコア](/images/jp-digest-20260807-ai-agent-long-term-memory/figure3.png)

いま基準になっているベンチマークは3つあります。LoCoMo、LongMemEval、BEAM です。

LoCoMo（2024年）は、複数セッションにまたがる会話の連続性を測ります。1会話あたり約300ターン、平均9,000トークン、最大35セッション。タスクはQA（質問応答）・イベント要約・マルチモーダル対話生成です。

LongMemEval（2024年）は、5つの能力を測ります。情報抽出、複数セッション推論、時間推論、知識の更新、棄権です。LongMemEval_S は約115Kトークン・40セッション、LongMemEval_M は約500セッション。「存在しない出来事について聞かれたら答えない」という棄権の採点があるのが特徴です。これ、地味だけど大事ですよね。

BEAM（2026年・ICLR）は、10種類の記憶能力を測ります。100会話・最大1,000万トークン・1会話あたり2,000問。BEAM-1M と BEAM-10M の2トラックです。1,000万トークン、早すぎません？

Mem0 の報告スコアはこうです。すべて Mem0 の自社報告なので、そのつもりで見てくださいね。

| ベンチマーク | スコア |
|---|---:|
| LoCoMo 全体 | 92.5% |
| LoCoMo 時間に関する質問 | 92% |
| LoCoMo マルチホップ（複数の情報をつないで答える） | 91% |
| LoCoMo オープンドメイン検索 | 72.7% |
| LongMemEval 単一セッション（ユーザー発話） | 98.6% |
| LongMemEval 知識の更新 | 93.6% |
| LongMemEval 複数セッション | 88.0% |
| BEAM-1M | 64.1% |
| BEAM-10M | 48.6% |

BEAM-10M になると半分を割ります。ここはかなり生々しいです。

トークンとレイテンシも見逃せません。検索1回あたり平均 6.7K〜7.0K トークン。全部を文脈に詰め込む方式は1クエリあたり 25,000トークン超です。トークンが1万どころじゃなく違うんです。P50レイテンシは全ベンチで 1.1秒以下。一方で、全文詰め込み方式は精度は出るもののレイテンシが厳しく、Mem0 チームによる LOCOMO 評価では、中央値 9.87秒、p95 17.12秒でした。

出典は Mem0 公式ブログ "AI Memory Benchmarks 2026: LoCoMo, LongMemEval & BEAM"（2026年7月31日）です。

ただし、限界もあります。しかも Mem0 自身が自社ブログで認めています。

- LoCoMo は 2026年の基準では文脈長が短めで、しかも「知識の更新」を明示的に採点していない。
- LongMemEval も、評価しているのは主に「読み出し」であって、「何を書き込むか」の質は測れていない。
- BEAM はまだどのアーキテクチャも飽和させられていない。つまり伸びしろだらけ。
- 公開ベンチが測れていないものとして、数年スケールの継続、書き込みステップの質、忘却と統合、同時アクセス時のユーザーごとの分離、トークン経済がある。

作った本人がここまで正直に書いてるのは、逆に信用しやすいところでもあります。

## 実装は3方式。どれも思想がぜんぜん違う

![記憶の実装3方式（抽出型・OS型・グラフ型）の比較](/images/jp-digest-20260807-ai-agent-long-term-memory/figure4.png)

### 抽出型：会話から「事実」を抜き出す

代表は Mem0 です。会話から「事実」を抜き出して外部に保存します。スコープは user_id / agent_id / run_id・session_id / app_id・org_id の4軸です。

v3 からは、2回なめて突き合わせる方式をやめて、単一パスの追記型になりました。事実が変わると、新しい版が古い版の隣に並び、両方が残ります。矛盾の解決は検索するときに回されるんです。

これはけっこう面白い割り切りです。掃除を後回しにする代わりに、書き込みを安くする設計なんですよね。夏休みの宿題を未来の自分に投げる感じです。未来の自分、がんばれ。

検索は、意味の近さを使うベクトル、キーワード一致の BM25、エンティティ一致を混ぜたハイブリッドです。保存先は差し替え可能で、Qdrant や、pgvector を入れた PostgreSQL などを使えます。p95レイテンシは約1.44秒と報告されています。全部詰め込みの17.12秒に対して、かなり軽いです。

### OS型：エージェント自身に記憶を管理させる

代表は Letta、旧 MemGPT です。コンテキストウィンドウ（文脈窓）を RAM、アーカイバルメモリ（ベクトルDB）とリコールメモリ（過去メッセージ）をディスクに見立てます。OSのページングそのままの発想です。

特徴的なのは、裏で勝手に抽出しないところ。エージェント自身が推論の途中で memory_replace や archival_memory_insert といったツールを呼んで、自分の記憶を出し入れします。

検索はベクトル＋全文検索のハイブリッドで、リシプロカル・ランク・フュージョン（複数の検索結果の順位を混ぜる手法）で統合します。

ただし、引き換えにエージェント側の賢さを要求します。自分で自分の机を片付けられる人間じゃないと成立しない、みたいな話です。机の上がすぐ雪崩になるタイプには、ちょっと厳しいやつですね。

### グラフ型：関係と変化をそのまま持つ

代表は Zep（Graphiti エンジン）と Cognee です。エンティティ（人・物・概念）を抽出し、型と日付のついたエッジ（関係の線）でつなぎます。

強いのは、関係とその変化を持てるところです。時系列で事実を上書き・無効化できるので、「先月までの住所」と「今の住所」を区別して持てます。人間関係の相関図に、更新履歴まで付いている感じです。探偵の壁に貼ってある紐つき写真、あれのデータ版ですね。

Zep は会話履歴を進行的に要約して圧縮しつつ、意味検索と時間検索の両方を提供します。Cognee はグラフをネイティブに持つ設計で、複数ソースの取り込みと、文書が多いワークフローに向きます。

## エージェントが「寝てる間」に記憶を整理する

![sleep-time compute の流れ](/images/jp-digest-20260807-ai-agent-long-term-memory/figure5.png)

sleep-time compute（スリープタイム計算）という考え方があります。人間が話しかけていない、暇な時間に記憶を整えておく仕組みです。

構成は2体のエージェントです。

- 主エージェント  
  ユーザーに返事をし、ツールを呼び、外部メモリを検索します。ただしコアメモリ（常に文脈に載っている記憶）を書き換えるツールは持たされていません。

- スリープタイムエージェント  
  主エージェントがアイドルの間に、主エージェントのコアメモリと自分のコアメモリの両方を管理・書き換えします。

人間が寝ている間に記憶を定着させる、というたとえがかなり近いです。ただし「AIが夢を見る」みたいな話ではなく、会話していない時間にメモリを整備するという実装上の工夫です。

これをやると、記憶の管理を会話の最中から追い出せます。会話中にお片付けしないで済むので、レイテンシが乗りにくくなり、安定性も良くなるわけです。ユーザーを待たせながら棚卸ししない、というだけでもだいぶえらいです。

元になった論文は "Sleep-time compute: Beyond inference scaling at test-time"（arXiv:2504.13171、Lin, Snell, Wang, Packer, Wooders, Stoica, Gonzalez、2025年）です。数学のベンチマーク AIME と GSM で、パレート改善（どこかを犠牲にせずに全体が良くなること）が示されています。実装として入ったのは Letta 0.7.0（2025年4月21日公開）です。

## 本丸は「覚えること」じゃなくて「忘れること」

ここまでは「どう覚えるか」の話でした。でも、いちばんヒヤッとするのはこの先なんです。

2026年4月21日に投稿され、ACL 2026 Findings に採択された論文があります。"From Recall to Forgetting: Benchmarking Long-Term Memory for Personalized Agents"（arXiv:2604.20006、Md Nayem Uddin, Kumar Shubham, Eduardo Blanco, Chitta Baral, Gengyu Wang）です。

この論文の問題提起はかなり直球です。既存のベンチマークは、長期記憶の評価を「過去の会話から事実を取り出せるか」に寄せすぎている。だから、記憶を時間をかけて統合できているか、頻繁な知識更新をさばけているかが、ほとんど見えないんです。

提案されたベンチマークが Memora です。数週間〜数ヶ月にわたるユーザーとの会話をカバーし、記憶に根ざした3つのタスクを評価します。remembering、つまり覚えている。reasoning、それを使って考える。recommending、それを使って勧める。データ品質は自動チェックと人手評価の両方で担保されています。

キモは FAMA（Forgetting-Aware Memory Accuracy、忘却を考慮した記憶精度）という指標です。古くなった記憶、無効になった記憶に頼って答えたら減点されます。

たとえば、友人が引っ越したのに、ずっと前の住所を覚えたまま案内してくる人。しかも「たまたま近くまで着けたからセーフ」で済まされたら、さすがにモヤッとしますよね。答えが合ってれば根拠が古くてもOK、っていう採点、よく考えたら怖くないですか？

4つのLLMと6つのメモリエージェントを評価した結果、無効な記憶の再利用が頻繁に起きていて、変化していく記憶を突き合わせることに失敗していました。論文の言い方では、メモリエージェントがもたらす改善は marginal（限定的）です。この温度感は、やわらげずに受け止めたいところです。

なぜ今まで見えなかったかというと、従来の評価は「記憶を入れたこと」に報酬を与える設計で、「記憶の誤用」を見ていなかったからです。最終的な答えが合っていれば、無効な記憶に頼っていても減点されませんでした。

つまり、2026年の長期記憶で本当に難しいのは、たくさん覚えることではありません。古い記憶を疑い、統合し、必要なら捨てることなんです。冷蔵庫と同じで、入れるより賞味期限を見るほうが大事だった、という話です。

## で、自分のプロダクトでは何を選べばいい？

![記憶レイヤーを選ぶための4つの質問](/images/jp-digest-20260807-ai-agent-long-term-memory/figure6.png)

判断は、まず4つの問いに分けると考えやすいです。

1. 覚えさせたいのは「事実」か「関係」か  
   単発の事実なら抽出型が合いやすいです。人・物のつながりとその変化を追うなら、グラフ型が向いています。メモ帳で足りる話なのか、相関図が必要な話なのか、という見方です。

2. その事実は頻繁に変わるか  
   変わるなら、更新と無効化の仕組みがある方式を最優先にしたいです。追記だけして矛盾を検索時に解く設計は、ここが弱点になりうるからです。未来の検索に掃除を押しつけすぎると、あとで泣きます。

3. 応答のレイテンシは何秒まで許せるか  
   全部を文脈に詰め込む方式は、中央値 9.87秒・p95 17.12秒という報告があります。記憶レイヤーを挟むと、検索1回あたり6.7K〜7.0Kトークン、P50で1.1秒以下です。待てるプロダクトか、待てないプロダクトかで選び方はかなり変わります。

4. 誰の記憶かをちゃんと分離できるか  
   公開ベンチマークは、同時アクセス時のユーザーごとの分離をどれも測っていません。ここは自分で検証するしかないです。記憶の混線は、ちょっとしたバグでは済まないやつですよね。

すでに使っているエージェントフレームワークがあるなら、そこに素直に載る記憶レイヤーを選ぶのが結局いちばん早いです。主要フレームワークへの連携は各社そろえています。

そして、どの方式を選んでも「古い記憶をどう捨てるか」は自分で設計する必要があります。そこはまだ誰も解けていません。結局いちばん大事なのは、ベンチのスコアではなく「あなたのデータがどれくらいの速さで古くなるか」なんです。

## まとめ

- 記憶は、エージェントにあとから足す機能ではなく、独立した設計テーマになりました。
- 実装は大きく、抽出型・OS型・グラフ型の3系統です。
- ベンチのスコアは高く見えますが、自社報告であり、しかも知識更新を十分に測れていない部分があります。
- 査読論文レベルで見ると、無効な記憶の再利用はまだ頻発しています。
- sleep-time compute のように、「暇な時間に整える」発想も出てきています。

まずは、自分のプロダクトのデータにどれくらいの賞味期限があるのかを測ってみてください。何を覚えるかより、いつ忘れるべきかのほうが、たぶん先に効いてきます。
