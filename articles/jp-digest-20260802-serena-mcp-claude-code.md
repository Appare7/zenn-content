AIにコードを直させたら、関係ないファイルを延々とgrep（文字列検索）して、気づいたらトークン代（AIに払う従量課金）だけ溶けてた……みたいなこと、ありますよね。

この記事では、複数の海外記事・公式発表をもとに、「コーディングエージェント（AIがコードを読み書きするツール）に、grepじゃなくてIDE（統合開発環境）の索引を持たせるべきか？」という論争を整理してみます。

Serena（セリーナ）みたいなMCP（AIツールに外部機能をつなぐ共通規格）サーバーを入れると本当に速く安くなるのか。逆に、grepで十分な場面もあるのか。ここを、ちょっと冷静に見ていきます。

![grepで探すか、索引を持たせるか](/images/jp-digest-20260802-serena-mcp-claude-code/figure1.png)

## そもそも何が問題になってるの？

AIコーディングエージェントって、コードを読めます。書けます。推論もできます。  
でも、コードがどう繋がっているかを理解していないせいで、普通に壊すことがあるんです。

Ry Walkerの調査記事「Code Intelligence Tools」（2026年3月15日公開／6月11日更新）では、この問題がかなり分かりやすく語られています。たとえば、こんな感じです。

- ある関数を、それを呼んでいる他の47個の関数を知らないまま書き換える
- クラス名を変えるのに、それをimport（外部の部品を読み込むこと）している連鎖を追わない
- モジュール（まとまった機能単位）をリファクタ（動きは変えずにコードを整理すること）するのに、影響範囲（blast radius＝どこまで壊れるか）を確認しない

人間なら「この関数、どこから呼ばれてるんだっけ？」と確認してから触るところを、エージェントが勢いで直してしまう。ここが怖いんですよね。

そこで出てきたのが「コードインテリジェンス（コードの構造をあらかじめ解析して使えるようにする仕組み）系ツール」です。

ざっくり言うと、コードベース（プロジェクト全体のコード）をただのテキストの山として扱うのではなく、事前にこういうものを作っておきます。

- ナレッジグラフ（コードの繋がりを図として持つもの）
- シンボル索引（関数やクラスなど、意味の単位を探せる索引）
- セマンティック検索（意味にもとづく検索）
- 依存関係マップ（何が何に依存しているかの地図）

そして、それをMCPやCLI（コマンドで操作する窓口）、API（プログラムから呼ぶ窓口）経由でエージェントに渡す、というわけです。

Ry Walkerの調査では、この分野のツールを**14個**、4つの階層に分類しています。

- 階層1 ナレッジグラフ系: CodeGraph、GitNexus、CodeGraphContext、Axon
- 階層2 シンボル／セマンティック検索系: Serena、claude-context、grepai、Octocode MCP ほか
- 階層3 コンテキスト詰め込み系: Repomix、code2prompt、Aiderのrepo-map ほか
- 階層4 商用: Augment Context Engine、Sourcegraph Cody、DeepWiki、Greptile

伸び方もかなり速いです。CodeGraphは2026年1月18日ローンチで5か月足らずで47.4k star、GitNexusは4月時点の約1.2kから6月に42kへ。カテゴリごと一気に立ち上がった感じがあります。

## Serenaって何をしてくれるの？

SerenaはオープンソースのMCPサーバーです。GitHubのoraios/serenaリポジトリで公開されていて、**MITライセンス、27.4k star**。リポジトリの説明文はこうです。

> A powerful MCP toolkit for coding, providing semantic retrieval and editing capabilities - the IDE for your agent

日本語にすると、「コーディング用の強力なMCPツールキット。意味を理解した検索と編集ができる＝エージェントのためのIDE」くらいの感じですね。

何が違うかというと、Serenaはコードベースを「grepする対象のテキストの塊」としてではなく、**LSP（Language Server Protocol＝エディタがコードの意味を解析するための共通の仕組み）経由でシンボル（関数やクラスといった意味の単位）として扱う**ところです。

提供しているツールは、大きく見るとこんなカテゴリです。

- 検索系
  - シンボルを名前で探す
  - ファイルの構造だけを俯瞰する
  - 参照元をすべて辿る
  - 型の階層を見る
  - 実装を探す
- リファクタ系
  - シンボルのリネーム
  - コードの移動
  - 関数のインライン化
  - 削除の波及処理
- 編集系
  - 関数やクラスの中身だけを差し替える
  - シンボルの前後に挿入する
  - 安全に削除する

具体的なツール名でいうと、`find_symbol`（名前でシンボルを探す）、`get_symbols_overview`（ファイル全体を読まずに構造の目次だけ取る）、`find_referencing_symbols`（そのシンボルを使っている箇所を全部洗い出す）、`replace_symbol_body`（関数の中身だけ差し替える）などがあります。

対応言語は**40以上**。バックエンド（裏側で動く仕組み）は2種類で、無料のオープンソースなランゲージサーバー方式と、JetBrainsのプラグイン方式（有料・無料トライアルあり）があります。Python、JavaScript、TypeScript、Java、Go、Rust、C/C++ などに対応しています。

連携先としては、Claude Code、Codex、Claude Desktop、MCP対応のIDE（VSCode、Cursor、JetBrains）があります。

インストールは、公式READMEでは次の2行です。

```bash
uv tool install -p 3.13 serena-agent
serena init
```

ここでかなり大事な注意点があります。  
**公式が「MCPやプラグインのマーケットプレイス経由でSerenaを入れないでください」と明確に警告しています。**

理由は、そこに載っているインストールコマンドが古いからです。こういうところ、地味にハマるやつなので、公式リポジトリを見るのが安全ですね。

Teknasyon Engineeringの解説記事では、実務的なポイントとして `ignored_paths`（無視するパス）の設定にも触れています。node_modules だけで8万ファイル超えることがあるからです。そこを除外しないと、検索対象が膨れ上がってしまうんですよね。

効果としては、検索の誤ヒットが減る、参照漏れのないファイル横断リファクタができる、ファイル丸ごと読ませずシンボル単位で聞けるのでトークンが浮く、といった点が挙げられています。

## 「めちゃくちゃ効く」側の数字

ここまで読むと、「じゃあもう全員Serenaとかコードインテリジェンス系ツールを入れればよくない？」となりそうです。実際、効いた側の数字はかなり派手です。

Ry Walkerの調査記事では、次のような数字がまとめられています。どれも出典元の但し書き付きで見てください。

- grepai: Claude Codeの入力トークンが**97%減**（独立系のベンチマークとされる）
- GitNexus: **ツール呼び出し88%減、トークン74%削減**（本番環境の監査より）
- CodeGraph: **ツール呼び出し58〜70%減**（ベンダー発表と独立レビュー）
- Augment Context Engine: **エージェントの品質70%以上向上**（※ベンダー自己申告）

別ソースとして、Anthony Westの調査記事では、Codebase-Memory がかなり有力な証拠として挙げられています。これは、Tree-sitter（コードを構文の木に変換する解析ツール）ベースのナレッジグラフをMCPで公開する方式です。

Codebase-Memory は、**トークン10分の1、ツール呼び出し2.1分の1** を31リポジトリで報告しています。

ただし、ここも大事です。著者自身が「これは1つのシステム、1つの評価設計、1本の論文にすぎない」と釘を刺しています。

数字だけ見ると、「今すぐ入れなきゃ損じゃん」となりますよね。97%減とか10分の1とか、強すぎます。  
でも、**ほぼ全部が作った側の計測かそれに近い**んです。ここが、次の話に効いてきます。

## 冷や水：入れたのに高くなった実験がある

ここがこの記事のいちばんの読みどころです。

2026年5月4日、JetBrainsのAIチーム（著者 Denis Shiryaev）が、「エージェントにIDEネイティブの検索ツールを渡したら、速く・安くなった」という実験記事を公開しました。タイトルは "We Gave Agents IDE-Native Search Tools. They Got Faster and Cheaper." です。

渡したものは、ファイル検索・テキスト検索・正規表現・シンボル検索の4モードを束ねたMCPツールと、それを使わせるためのスキル（あらかじめ同梱した検索の指示書）でした。

狙いは、grepやfindの代わりにIDEの索引・AST（抽象構文木）・プロジェクトモデルを使わせることです。これはかなり自然な発想ですよね。人間の開発者もIDEのジャンプや参照検索を使うわけなので。

当初の結果は、かなり好意的でした。

- 中央値のレイテンシ（応答時間）が**8.33%短縮**（83.11秒→79.03秒）
- P95（遅い方から5%のライン）で**16.44%短縮**（268.71秒→213.17秒）
- 総コストが**5.60%減**（44.17ドル→41.67ドル）
- 1タスク0.50ドルの予算超過率が**33.28%改善**（6.67%→4.44%）
- 品質（テスト通過）は統計的に有意な変化なし

ところが、2026年7月29日、同じ記事の冒頭に訂正が入りました。原文では、こう書かれています。

> We got an important part of this experiment wrong.

「この実験の重要な部分を間違えていました」ということです。

中身はこうでした。検索スキルは読み込まれていたものの、**その裏にあるIDEのMCPツールは実際には呼ばれていなかった**んです。

エージェントは普通のシェルのツール（grepなど）を使っていて、チャットのUIがその呼び出しの一部を「Search」と表示していたため、IDEネイティブ検索だと読み違えた、と。

さらにJetBrainsは、「品質・レイテンシ・コストの数字自体は本物で統計計算も正しい。だが説明が間違っていた。この実験が比較していたのは、素のエージェントと**"検索の指示が追加で入ったエージェント"**だった」と書いています。

ここ、かなり正直ですよね。

その後、設定を直して測り直した追試の結果が重要です。GPT-5.4 / GPT-5.5 / GPT-5.6 を使って**2,700トラジェクトリ（エージェントの実行経路）**を再実行したところ、こうなりました。

- GPT-5.4-mini と GPT-5.5 は **IDE検索ツールを一度も呼ばなかった**
- GPT-5.6 は675トラジェクトリ中616〜660回と、ちゃんと使った
- ただし、GPT-5.6では**コストは下がるどころか上がった**
  - 低い推論レベルで約6〜7%増
  - 中程度で全体コスト10%増
  - P95のコストは約15%増

JetBrainsの結論も、かなり抑制的です。

> this setup has not earned a default-on rollout.

「この構成はデフォルトONにするだけの根拠を得られなかった」ということですね。さらに、「特定のタスクでは効くかもしれないが、モデルをまたいで安定した効果は見つからなかった」とも書いています。

「ツールを渡したのに、モデルがそもそも呼ばない」って、道具箱を置いただけで職人が使ってくれない話とそっくりです。MCPサーバーを入れて満足しがちですが、**入れることと使わせることは別問題**なんですよね。

## grep派の言い分もちゃんと聞く

ここで、grep派の話もちゃんと聞いておきたいです。Claude Codeは、意図的に索引を作らない設計を取っています。

2026年5月14日の公式記事「How Claude Code works in large codebases」によると、Claude Codeは「ファイルシステムを歩き回り、ファイルを読み、grepで必要なものを正確に見つけ、コードベース中の参照を辿る」やり方をします。つまり、人間のエンジニアと同じように探す、という発想です。

この方式ではローカルで動き、索引をビルド・保守・サーバーにアップロードする必要がありません。

なぜRAG（外部データを検索してAIに渡す仕組み）を採らないのか、という理屈も書かれています。

コードベース全体を埋め込み（ベクトル化）して、質問時に関連チャンク（分割された断片）を取り出す方式は、大規模になると埋め込みのパイプラインが活発な開発チームの速度に追いつけない。開発者が検索する頃には、索引は数週間前・数日前・数時間前のコードベースを映している、という話です。

たしかに、古い索引を自信満々に渡されるのは怖いですよね。  
エージェントが「この関数はここからしか呼ばれていません」と言ってきたけど、それが数時間前の世界線だったら困ります。

ただし、公式もトレードオフを認めています。エージェント検索はそうした失敗モードを避けられる一方で、**Claudeがどこを見ればいいか分かるだけの初期コンテキストがあるときに一番うまく動く**、というわけです。

だから公式は、大規模コードベース向けに、次のような"ハーネス"（土台の作り込み）を勧めています。

- CLAUDE.md（毎回自動で読まれる指示ファイル）を薄く階層的に置く
- リポジトリのルートではなくサブディレクトリで作業を始める
- フック・スキル・プラグイン・LSP連携・MCPサーバー・サブエージェント（探索用の隔離されたインスタンス）を組み合わせる

つまり、「索引なしで魔法のように全部分かる」という話ではありません。grepで探すにしても、探しやすい足場は作ってあげる必要があるんです。

Anthony Westの調査では、索引側の弱点も挙げられています。

- 意味の正確さにはお金と保守コストがかかる。SCIP（コードの意味情報を交換するための索引形式）やLSPの仕組みは言語ごとの道具立てと運用が必要
- ビルドが壊れていたり、索引を作った時と依存関係が違うと、意味解析系の方式は機能しなくなる
- 索引の鮮度・信頼度・出所を保証する標準がまだ無いので、エージェントが古い情報を引く可能性がある
- 「構文ベースの地図は地味だから過小評価されている」が、ビルド不要という強みがある

索引は強い。でも、索引は古くなるし、壊れるし、保守もいる。grepは素朴。でも、いま目の前にあるファイルを見る。ここはかなり本質的な分かれ道です。

## で、結局どう使い分ければいい？

ここまで見ると、「Serenaを入れるべき」「いやgrepで十分」と白黒つけたくなります。  
でも、たぶん現実はもう少し地味です。**効く場面と効かない場面がある**、がいちばん近いと思います。

入れて効きやすいのは、たとえばこういう場面です。

- 大規模で参照が絡み合ったリポジトリ
- シンボルのリネームや影響範囲を追うリファクタ
- 「この関数、どこから呼ばれてる？」を何度も聞くタイプの作業

Serenaの `find_referencing_symbols` や `get_symbols_overview` は、この用途がまさに本業です。ファイル全体を読ませる前に、構造の目次だけ取る。関数を触る前に参照元を洗う。これは人間がIDEでやっていることに近いですよね。

逆に、効きにくい、あるいはかえって損になりやすい場面もあります。

- 小さいリポジトリで、grepで一発で見つかる
- 作業のたびにコードが激しく変わっていて、索引が追いつかない
- 使っているモデルが、そのツールを呼んでくれない

最後が特に大事です。JetBrainsの追試がまさにそれでした。ツールを渡しても、モデルによっては一度も呼ばない。呼んだとしても、コストが下がるとは限らない。ここ、忘れると危ないです。

導入したら、最低限これだけは見てみてください。

1. エージェントのログやツール呼び出し履歴を見て、**そのMCPツールが実際に呼ばれているか**を確認する  
   UIの表示名だけを信じないでください。JetBrainsが踏んだ罠がこれです。

2. 入れる前と後で、トークン消費とタスク完了までの時間を自分の環境で測る  
   ベンダーの数字ではなく、自分のリポジトリでの数字を見るのが大事です。

3. `ignored_paths` で node_modules のような巨大ディレクトリを除外する  
   いらないものまで見せると、せっかくの索引もノイズだらけになります。

4. モデルを変えたら測り直す  
   モデルによってツールを呼ぶ率がまるで違います。同じ設定でも、結果が変わる前提でいたほうがよさそうです。

一言でまとめるなら、**銀の弾丸ではないが、当たる場面でははっきり当たる**。このくらいの温度感がちょうどよさそうです。

## まとめ

コードインテリジェンス分野は、2026年に一気に立ち上がりました。コードの構造をあらかじめ索引化してエージェントに渡す、という発想です。

Serenaはその中でも分かりやすい選択肢で、27.4k star、MITライセンス、40以上の言語に対応。Claude CodeにもCodexにも挿せます。

一方で、削減率の数字はかなり派手です。97%、88%、74%、10分の1。見るだけなら夢があります。  
ただし、出どころは作った側の計測が中心です。そこは冷静に見たいところです。

そしてJetBrainsは、自分たちの好意的な実験結果を2026年7月29日に自ら訂正しました。追試では、「デフォルトONにする根拠は得られなかった」と書き、コストが増えた組み合わせもありました。

Claude Codeが索引を持たないのも、手抜きではありません。「索引は古くなる」という設計判断があります。grepでいまのファイルを見る強さも、ちゃんとあるんです。

なので、着地はシンプルです。

まず自分のリポジトリで測ってみる。  
そして、入れたMCPツールが本当に呼ばれているか確認する。

Serenaは便利な道具になりえます。でも、置いただけで勝手に効く魔法の箱ではありません。自分のコードベース、自分のモデル、自分の作業でどう動くか。そこを見ながら、ちょうどいい距離感で付き合っていきたいですね。
