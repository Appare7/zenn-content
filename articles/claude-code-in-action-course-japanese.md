## 🕹️ 1. 長時間セッションを操縦する

コースが最初に教えるのは、長いセッションの習慣は2つだけ、ということです。**始める前に作業範囲を決める** ことと、**実行中に操縦する** こと。✅ 任せて離れるコースの1レッスン目が、ハンドルの握り方から始まるんですね。道具は6つ出てきます。

![](/images/claude-code-in-action-course-japanese/figure02.png)
*長時間セッションの習慣は2つ、出てくる道具は6つです*

### 始める前：計画は「実際に読む」

Planモード（プランモード／読み取り専用で調査して、計画を出すモード）は101でも主役でした。今回コースが念を押していたのは、出てきた計画の読み方です。「ざっと目を通すだけではいけません。実際に読む」。計画を反復する方が、走らせて後で片付けるより速い、というのが理由でした。💡 サッカーで言えば、戦術ボードの上で直すのはタダですが、失点してから直すのは高くつくわけです。

### 実行中：`/compact` は単独で打たない

`/compact`（コンパクト／ここまでの会話を要約して圧縮するコマンド）は、単独で打ちません。後ろに指示を書くんです。

```text
/compact Focus on the --version flag implementation
```

後ろに書いたものが、「要約が何を保持するか」を決めます。何も書かずに打っていた自分は、何を残すかを運に任せていたわけだ。🚀 次に `/compact` を打つときは、後ろに一言足してみて。

### 巻き戻しは5択

チェックポイント（checkpoint／巻き戻し用の保存地点）は、ユーザーのプロンプトのたびに作られます。空のプロンプトで `Esc` を2回押すと、選択肢が5つ出てきます。

| 選択肢 | 補足 |
| --- | --- |
| コードと会話を復元 | ―― |
| 会話を復元 | ―― |
| コードを復元 | ―― |
| ここから要約 | チェックポイント以降を要約。脇道の会話を畳む |
| ここまで要約 | 以前を要約。長いセットアップを畳んで実装は残す |

🔥 面白いのは下の2つですね。巻き戻しは「戻す」だけの道具だと思っていたんですが、「畳む」こともできるんです！脇道に逸れた会話だけを要約にして、本筋は残す。そういう使い方ができます。

![](/images/claude-code-in-action-course-japanese/figure03.png)
*巻き戻しの5択。下の2つは、戻すのではなく会話を要約に畳みます*

### `/goal`：完了条件を書いて走らせる

`/goal`（ゴール／完了条件を指定するコマンド）に条件を書くと、高速な評価者が「条件を満たした」と確認するまで、複数ターン続けてくれます。

```text
/goal all tests in src/billing pass, and the type checker reports zero errors
```

取り消しは `/goal clear` です。⚠️ 制約が1つあって、**評価者はトランスクリプト（transcript／会話の記録）しか読みません**。だから条件は、テスト結果のように、出力から確認できるものにします。

![](/images/claude-code-in-action-course-japanese/figure23.png)
*完了を判定する評価者が読むのは会話の記録だけです。条件は、出力から確かめられる形で書きます*


### ループとworktree

ループは、ターンの間に一定間隔でプロンプトを実行する仕組みです。間隔は固定か、自己ペース。CI（継続的インテグレーション／自動テストの仕組み）やデプロイ（deploy／本番への反映）の監視に使います。止めるのは `Esc` ですね。

worktree（ワークツリー／エージェントごとに用意する独立したファイルツリー）は、同じコードベースで複数のエージェントを動かすときに使います。コースの言い方は「1台の車に2つのハンドルは危険」でした。クリーンなworktreeは、終了時に自動で削除されます。各worktreeへコピーしたいgit管理外のファイル（環境変数ファイルなど）は、`.worktreeinclude` に列挙しておきます。

![](/images/claude-code-in-action-course-japanese/figure04.png)
*同じ作業ツリーで2体を動かす代わりに、エージェントごとにworktreeを用意します*

## 📝 2. CLAUDE.mdを引き締める

101では CLAUDE.md（クロード・エムディー／セッション開始時に毎回読まれる、プロジェクトの説明書）を「消えない記憶の置き場所」として紹介しました。今回はその続きで、**どう書けば従ってもらえるか** の話です。

⚠️ コースが最初に挙げる落とし穴は、ルールを足し続けて巨大化することでした。すると、Claudeが一部を無視し始めます。これはバグではなく、仕組みなんですよ。CLAUDE.md は強制される設定ではなく、ガイダンス（guidance／手引き）です。そして、全行が注意を奪い合います。コースの結論は「引き締まっているほど、より多く従う」でした。筋トレと同じで、増やすのは簡単なのに、絞る方がずっときついんですよね。

![](/images/claude-code-in-action-course-japanese/figure05.png)
*全行が注意を奪い合うので、引き締まっているほど従ってもらえます*

### まず「CLAUDE.mdが適切な手段か」を問う

🤔 書き足す前に、コースは問いを一つ挟みます。そのルールは、CLAUDE.md が適切な手段なのか、と。たとえば「mainに直接pushしない」のような絶対ルールは、PreToolUse（プリ・ツール・ユース／ツールが呼ばれる直前）のフック（hook／決まったタイミングで必ず実行される仕組み）に置きます。「ほとんどの場合」では足りないものは、フックへ。これが線引きです。

これ、自分の CLAUDE.md にも思いっきり心当たりがあった。引っ越しの実物は9節に書きますね。

### 置き場は4つ

| 場所 | 中身 |
| --- | --- |
| 管理ポリシー | 組織のもの。除外不可 |
| ユーザー | 自分の全プロジェクト |
| プロジェクト | チーム共有。コミットする |
| ローカル | git無視。このリポジトリの自分用メモ |

4つは、起動時に全部が積み重なります。どれか1つが選ばれるわけではないんですね。

### インポートは整理であって、節約ではない

長くなってきたら、別ファイルに分けてインポート（import／取り込み）できます。書き方は `@.claude/conventions/code-style.md` のように、`@` とパスです。

💡 ただ、ここに誤解しやすい点があります。**整理には効くけれど、読み込み量は減りません**。起動時に全部展開されるからです。ファイルを分けて軽くなった気がしても、読まれる量は同じなんですよ！

![](/images/claude-code-in-action-course-japanese/figure06.png)
*インポートで分けても、起動時に全部展開されるので読み込み量は同じです*

### 言い回しの3原則

| 原則 | 直す前 | 直した後 |
| --- | --- | --- |
| 具体的で検証可能に | APIルートのベストプラクティスに従う | 新しいAPIルートはsrc/api/handlersに、1ファイルにつき1つ |
| 禁止だけでなく代わりを示す | デフォルトエクスポートを使わない | デフォルトエクスポートではなく、名前付きエクスポートを使う |
| 強調は予算 | 全部が叫ぶと何も目立たない | IMPORTANT, YOU MUST は2〜3個まで |

3つ目の「強調は予算」という言い方が、いいですよね。大文字で叫べる回数には上限がある。使い切ったら、もう何も目立たないわけです。

![](/images/claude-code-in-action-course-japanese/figure24.png)
*強調は予算です。全部のルールが叫ぶと、どれも目立たなくなります*


### 改訂し続ける

✅ Claudeが間違えたら、それを CLAUDE.md へのバグ報告として扱います。その場で「それをCLAUDE.mdに追加して」と頼めるんです。消す側の基準もあって、「その行を正当化できないなら削除」。足すときも消すときも、理由が言えるかどうかで決めるんですね。

## 🔍 3. 最初に作るスキルは「検証」

スキル（skill／必要なときだけ読み込まれる手順書）を作るなら、何から作るか。コースの答えは「検証」でした。理由がいいんですよ。🤔 いまの確認作業は、「頼むのを忘れないこと」に依存しているから、なんです。こちらが頼み忘れた日は、確認も無いわけです。言われてみれば、その通りですよね。

検証スキルの流れは4段です。

1. テストスイート（test suite／テスト一式）を実行する
2. 差分を読む
3. **テストを通すためだけに弱められていないか** を確認する
4. 証拠を添えて、合否を報告する

スキルの記述（description／ディスクリプション。いつ使うかの説明文）に一致する場面になると、自動で発動します。⚠️ 効いているのは3番目ですね。テストが通ることと、テストが仕事をしていることは別なんです。テストを弱めて通す、人間もやるやつだ。

![](/images/claude-code-in-action-course-japanese/figure07.png)
*検証スキルの4段。3段目が、テストが仕事をしているかの確認です*

コースの定義も、そのまま引いておきます。

> 完了とは、ゲートが実行され、結果が観察され、明示的に述べられていること

ゲート（gate／通すか止めるかを決める関門）を実行した、結果を見た、言葉にして述べた。この3つが揃って、初めて完了なんですね。「たぶん通ると思います」は、まだ完了ではないわけです。

### 2回タイプしたら、それはスキル

何をスキルにするかの経験則は、シンプルでした。同じ複数ステップの指示を2回タイプしたら、それはスキル。🚀 同じ手順を2回打った覚えがあるなら、それ、今日スキルにして。

### フォルダ構成：SKILL.md は軽く

| ファイル | 扱い |
| --- | --- |
| SKILL.md | 軽く保つ |
| reference.md | 詳細を書く。必要なときだけ読まれる |
| check.sh などのスクリプト | 読み込まれず、実行される |

手順を全部 SKILL.md に書きたくなるんですが、そこを分けるんですね。細かい話は隣の reference.md に置いて、必要なときだけ読んでもらう。

💡 スクリプトが「読み込まれず、実行される」のもポイントです。検査の中身をスクリプトに寄せれば、SKILL.md は軽いままにできるんですよ！

### 置き場の整理

ここまでの3つの置き場を、コースは一枚にまとめていました。

| 置くもの | 置き場 |
| --- | --- |
| 常に適用される慣習 | CLAUDE.md |
| 特定のタスクの手順・資料 | スキル |
| 絶対に飛ばせないルール | フック |

![](/images/claude-code-in-action-course-japanese/figure08.png)
*慣習はCLAUDE.md、手順はスキル、飛ばせないルールはフックに置きます*

2節の「CLAUDE.md が適切な手段か」という問いの答えが、この表なんですよね。慣習なら CLAUDE.md、手順ならスキル、飛ばせないならフック。101の記事で書いた「お願いの層と強制の層」が、3つの置き場に整理された形です。

迷ったら、この表に戻ればいいわけです。そして `.claude/skills` にコミットしておけば、チーム全員が同じ検査を受け継ぎます。✅ 検証が個人の習慣ではなく、リポジトリの持ち物になるんですね。

## 🚦 4. 権限モードは6つ

101では3つと習った権限モードが、このコースでは6つ出てきます！数え方のズレは10節でまとめるとして、まずは一覧です。

| モード | 挙動 |
| --- | --- |
| Manual | 読み取りのみ無確認 |
| Accept edits | 読み取り・編集・一般的なファイル操作コマンドが無確認 |
| Plan | 調査と提案。編集しない |
| Auto | 全部受け入れるが、各アクションの前に別の分類器モデルがレビュー |
| Don't ask | 事前承認済みのツールだけ許可、他は確認なしで自動拒否 |
| Bypass permissions | 全チェックをスキップ。dangerously-skip-permissions と同等。隔離コンテナかVMの中だけ |

`Shift+Tab` で回るのは、manual / accept edits / plan / auto の4つです。現在のモードは、ステータスバーに出ます。

⚠️ Bypass permissions は、名前のとおり全チェックを飛ばします。使うのは、隔離コンテナ（container／外と切り離した実行環境）かVM（仮想マシン）の中だけです。

![](/images/claude-code-in-action-course-japanese/figure09.png)
*Shift+Tabで回るのは4つ。Don't askとBypass permissionsはその外にあります*

### Autoの分類器は何を止めるか

Auto は全部を受け入れます。ただし各アクションの前に、別の分類器（classifier／危険かどうかを仕分けるモデル）がレビューするんです。コースが挙げていた例はこうでした。

| ブロックする例 | 通す例 |
| --- | --- |
| 本番デプロイやマイグレーション | プロジェクト内の編集 |
| 強制プッシュ、ダウンロードしたコードをシェルに直接パイプ | ロックファイルからの依存インストール |
| 機密データの外部送信 | 読み取り専用のリクエスト |
| セッション前からあるファイルの不可逆な破壊 | 自分のブランチへのプッシュ |

表の言葉を補っておきますね。マイグレーション（migration）はデータベースの構造変更、ロックファイル（lockfile）は依存のバージョンを固定するファイルのことです。

### 分類器が見るのは意図で、正しさではない

🔥 この節でいちばん大事なのは、ここです。**分類器が見るのは意図で、正しさではない**。壊れた認証コードは、通ります。壊れていることは、危険ではないからです。壊れたコードが素通りする、と読んで二度見した。

サッカーの審判と同じなんですよね。危険なタックルには笛を吹くけれど、シュートが枠に飛ぶかどうかは見ていない。

だからコースは、Auto を「テストを実行する Stop フック」と組にします。✅ 前で意図、後で正しさ。安全と品質を、別々の仕組みで守るわけです！

![](/images/claude-code-in-action-course-japanese/figure10.png)
*Autoの分類器が意図を、テストを実行するStopフックが正しさを見ます*

### Don't ask は無人実行向け

Don't ask は、事前に承認したツールだけを許可して、それ以外は確認なしで自動拒否します。向いているのは無人実行です。CI、スケジュール、夜間バッチ（batch／まとめて実行する処理）ですね。💡 効き目は、承認待ちで止まらないこと。誰もいない時間に「許可しますか？」と聞かれても、答える人がいないじゃないですか。

## 🪝 5. フックで「必ず」にする

101では、フックのイベントを5つ紹介しました。このコースによると、イベントは約30あります！よく使うものはこのあたりです。

| イベント | 使いどころ |
| --- | --- |
| PreToolUse | 唯一、起こる前に止められる |
| PostToolUse | 自動フォーマット・リント |
| Stop | 「まだ終わっていない」と拒否できる。SubagentStop もある |
| PreCompact・PostCompact | 圧縮の前後 |
| InstructionsLoaded | 何が読み込まれたかの監査 |
| SessionStart | セッションの開始時 |

🔥 覚えておきたいのは、1行目です。起こる前に止められるのは、PreToolUse だけなんですよ。リント（lint／コードの書き方の機械チェック）のように「後から整える」仕事は、PostToolUse に置きます。

![](/images/claude-code-in-action-course-japanese/figure11.png)
*よく使うフックイベントの順番と、圧縮の前後に動くイベントです*

### 圧縮またぎの罠

⚠️ 圧縮の後にコンテキスト（context／Claudeの作業記憶）を再注入したいとき、選ぶのは PostCompact ではありません。**compact マッチャー（matcher／どの場面で動かすかの絞り込み条件）付きの SessionStart** です。名前だけ見ると PostCompact を選びたくなるので、コースも罠として挙げていました。

### PreToolUse は JSON で返す

PreToolUse の返し方は、JSON（ジェイソン／データを書く形式）を出力して、終了コード0です。`permissionDecision` に入れるのは allow / deny / ask のどれか。非対話の `-p` 用に、defer もあります。

```json
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"...","updatedInput":{"command":"..."}}}
```

### `updatedInput`：止めずに書き換える

💡 `updatedInput` を使うと、呼び出しを書き換えられます。ブロックではなく、リダクト（redact／伏せ字にすること）ですね。コースの例は、コマンド中の `sk_live_` パターンをプレースホルダ（placeholder／仮の文字列）に置換して、それでも実行させる、というものでした。

注意が1つあります。`updatedInput` は、入力オブジェクト全体を置き換えます。だから、変えないフィールドも書き戻す必要があるんです。

![](/images/claude-code-in-action-course-japanese/figure25.png)
*止める代わりに、入力を書き換えて通します。秘密の文字列だけを伏せて、コマンドは実行されます*


### 終了コードの罠

| 終了コード | 意味 |
| --- | --- |
| 0 | 成功 |
| 2 | ブロッキング。stderr が Claude に返る |
| それ以外 | 非ブロッキング |

stderr は標準エラー出力のことですね。そしてここが罠なんですが、**終了コード1は止めません**。エラーに見えるのに、Claude は続行するんです。1で止まらないのは、初見殺しだと思ったぜ。

ほかにも、イベントごとの違いがあります。

- 終了コード2は、Stop もブロックできる
- PostToolUse でのブロックは手遅れ（実行済み）。ただしテキストは返せる
- Notification や SessionStart は、ブロッキングを無視する

![](/images/claude-code-in-action-course-japanese/figure12.png)
*止めるのは終了コード2だけです。1は「それ以外」に入り、Claudeは続行します*

🚀 exit 1 で止めたつもりのフックが無いか、一回確かめてみて。

### ルーティン

ルーティンの中身は、プロンプト+リポジトリ+コネクタ（connector／外部サービスとの接続）+トリガー（trigger／起動のきっかけ）です。トリガーは3種類あります。

- cron（クーロン／定時実行の仕組み）
- APIエンドポイント（endpoint／リクエストを受け付ける窓口）へのHTTP POST
- GitHubイベント

作るのは claude.ai/code/routines か、このコマンドです。

```text
/schedule daily dependency audit at 9am
```

⚠️ 注意は3つありました。

- リサーチプレビュー（research preview／試験公開）である
- 繰り返しは、最短1時間ごと
- デフォルトブランチの新しいクローン（clone／リポジトリの複製）から開始する。`claude/` ブランチへは自由にpushでき、それ以外はチェックあり（保護ブランチ等は拒否）

### ヘッドレス

```bash
claude -p "summarize the changes in this diff"
```

標準入力を読んで、標準出力に書きます。

⚠️ ここは1つ、コースの説明と公式ドキュメントが食い違っていました。コースの本文は「`-p` はフック・スキル・プラグイン・MCP・CLAUDE.md の自動検出をスキップする。そのぶん起動が速い」と書いています。でも[公式ドキュメント](https://code.claude.com/docs/en/headless)では、自動検出をスキップして速くなるのは `--bare` を付けたときです。素の `-p` は、対話セッションと同じものを全部読み込みます。つまり、プロジェクトに置いたフックも、`-p` で普通に動くんです。「無人実行ではフックが効かない」と思い込むと危ないので、ここはドキュメントを正としてください。

結果を機械で扱うときは、構造化出力を使います。`--output-format json` と `--json-schema '...'` を付けると、`structured_output` フィールドに入ってくる。それを `jq`（ジェイキュー／JSONを加工するコマンド）で取り出します。複数ステップにしたいときは、JSON出力の session_id を使って再開です。

```bash
claude --resume "$(jq -r .session_id /tmp/plan.json)"
```

その先にあるのが `--bare` です。手元の設定を読み込まないので、どのマシンでも同じ結果になります。CI向けですね。💡 ドキュメントによると、`--bare` はログイン情報も読まないので、APIキーを環境変数で渡す必要があります。さらに先が Agent SDK で、TypeScript と Python があります。コースに出てくるのは、query 関数と、allowedTools・システムプロンプト・権限モードですね。

コースの助言は「まずルーティンから。必要になったときだけスペクトラムを下る」でした。下るのは必要になってから、か。順番、逆に考えていたかもしれない。

### GitHub：Code ReviewとAction

GitHubの上で動かす方法は2つあります。まず、マネージド（managed／運用を任せられる）の Code Review です。Claude GitHubアプリを、管理者が有効化します。動くタイミングは3通り。PR（プルリクエスト／変更をレビューしてもらう依頼）が開かれたとき一度、pushのたび、`@claude review` とコメントしたときだけ。コードベース全体に対して差分を分析して、インラインコメントを付けてくれます。重大度タグ、重複排除とランク付けもあります。

できないことも、はっきりしています。

- PRの承認・ブロックはしない（判断は人間）
- 自動修正はない
- リサーチプレビューで、team・enterprise プラン

修正はローカルでやります。`/code-review` が差分をレビューして、`--fix` で作業ツリーに適用ですね。

もう1つが GitHub Action です。入れるのは `/install-github-app`（管理者権限が要ります）。

```yaml
- uses: anthropics/claude-code-action@v1
  with:
    anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
    trigger_phrase: "@claude"
    claude_args: "--max-turns 5 --model claude-sonnet-5"
```

入力は、anthropic_api_key / github_token / trigger_phrase（既定 @claude）/ use_bedrock・use_vertex・use_foundry / prompt / claude_args です。`claude_args` がつまみになっていて、`--max-turns 5` で上限、ほかに権限モードと許可ツールを渡せます。レポートを作らせるだけなら、読み取り専用にするわけですね。

*まずマネージドのCode Reviewから。CIで実行が必要になったらGitHub Actionへ進みます*

✅ 使い分けもコースが一文で言っています。「まずマネージドから。CIで実際に何かを実行させる必要が出たらアクションへ」。ルーティンのときと同じで、軽い方から始めるんですね！

### インストール前に読む

⚠️ コースが強く言っていたのは、これです。**インストール前に読む**。プラグインは、あなたの権限でコードを実行します。スキル目当てで入れても、PreToolUse や Stop フックが一緒に付いてくるんですよ。そして、レビュー済みであることは、信頼できることと同じではありません。

スキルが欲しかっただけなのにフックも付いてくる、はちょっと怖い。

5節で見たとおり、フックは「必ず」動く仕組みです。自分で書いたフックなら頼もしいんですが、人が書いたフックも、同じように必ず動きます。だから読むのは、スキルの説明文だけでは足りません。フックの中身まで開いて読む、ということですね。

### 入れると何が変わるか

| 対象 | 入れたときの扱い |
| --- | --- |
| フック | 積み重なる（置き換えない） |
| スキル・エージェント・コマンド | 名前空間化される（`/plugin-name:skill-name`） |
| settings.json | agent キーと、サブエージェントのステータスラインキーだけ尊重 |
| agent キー | プラグインのサブエージェントをメインスレッドに昇格させる（既定の挙動が変わりうる） |

名前空間（namespace／名前の頭に付ける区切り）が付くので、どのプラグインのスキルかは名前で分かります。💡 一方でフックは積み重なるので、自分のフックに足される形になります。最後の agent キーは、既定の挙動そのものが変わりうるので、読むときに特に見ておきたい所ですね。

### CLAUDE.md から「絶対ルール」をフックに引っ越した

元の CLAUDE.md には、こう書いていました。「slug は 12〜50文字」「画像は1枚3MB以下。push前に npm run check-images」。slug（スラッグ／記事URLになるファイル名）も画像も、破るとリポジトリ全体のデプロイが止まります。⚠️ つまり、「ほとんどの場合」では足りないルールなんです。2節の線引きで言えば、フック行きですね。

そこで PreToolUse フックを書きました。`git push` を含むBash（バッシュ／シェルコマンドの実行）コマンドのときだけ動いて、違反があれば `permissionDecision: deny` を返します。

:::details .claude/hooks/guard-push.sh
```bash:.claude/hooks/guard-push.sh
#!/bin/bash
# PreToolUse(Bash): git push の前に、デプロイを止める違反がないか確かめる。
# 違反があれば permissionDecision: deny を返して push を止める。
input=$(cat)
cmd=$(echo "$input" | jq -r '.tool_input.command // empty')
case "$cmd" in *"git push"*) ;; *) exit 0 ;; esac
cd "${CLAUDE_PROJECT_DIR:-.}" || exit 0

problems=""
over=$(node scripts/check-images.mjs 2>/dev/null)
[ -n "$over" ] && problems+="3MBを超える画像がある: $(echo "$over" | tr '\n' ' ')"$'\n'
for f in articles/*.md; do
  s=$(basename "$f" .md)
  if [ ${#s} -lt 12 ] || [ ${#s} -gt 50 ] || ! [[ "$s" =~ ^[a-z0-9_-]+$ ]]; then
    problems+="slugが不正(12〜50文字の a-z0-9-_ ): $s"$'\n'
  fi
done

if [ -n "$problems" ]; then
  jq -n --arg r "$problems" '{hookSpecificOutput:{hookEventName:"PreToolUse",permissionDecision:"deny",permissionDecisionReason:$r}}'
fi
exit 0
```
:::

テストは3通りやりました。

| 試したこと | 結果 |
| --- | --- |
| 問題なしの状態で `git push` | 出力なし・終了コード0（許可） |
| `ls` | 素通り |
| わざと `articles/short.md` を置いて `git push` | 下の JSON が返る |

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "slugが不正(12〜50文字の a-z0-9-_ ): short\n"
  }
}
```

✅ 5節で見た形のJSONが、そのまま出てきました！CLAUDE.md の側は、2行を消して「書かなくてもフックが止める」の1行に置き換えています。お願いが2行減って、強制が1本増えたわけです。

![](/images/claude-code-in-action-course-japanese/figure18.png)
*CLAUDE.mdの2行を消して、push前に動くPreToolUseフックへ移しました*

### Stop フックで「検査に通るまで終わらせない」

検証スキルは、まだ「お願い」の層です。そこで7節の「約束ではなくゲートに」をやりました。`.claude/hooks/stop-verify.sh` は、記事を変更したターンだけ check.sh を走らせます。失敗なら stderr に FAIL 行を出して、**exit 2**。`stop_hook_active` が true なら、何もしません。これは無限ループの防止ですね。

わざと1枚のキャプションの `*` を外して、実行してみました。

```text
記事の検査に失敗。FAIL を直してから終わること:
== articles/claude-code-101-01-what-is-claude-code.md
== articles/claude-code-subagents-course-japanese.md
FAIL captions キャプション無し: 本文[5]行目
exit=2
```

止まりました！終了コード1と2の違いも、手元で確かめています。`exit 1` は非ブロッキングで、Claudeは続行。`exit 2` はブロッキング。5節の表のとおりでした。

ただ、ここで一度つまずいたんです。最初は「変更のあった記事すべて」を検査の対象にしようとしました。ところがリポジトリには、画像をまだ生成していない書きかけの記事がありました。gitでは未追跡のファイルです。これが毎回 FAIL になります。すると、どのターンも終われなくなるんですよ。

書きかけの記事は、検査に通らないのが普通の状態です。通らないのが普通のものにゲートを掛けたら、ゲートは毎回閉まります。自分で掛けた鍵に、自分が閉じ込められる形ですね。

解決は、対象を絞ることでした。`git diff --name-only HEAD`、つまり追跡済みの変更だけにしたんです。

🔥 ここで学んだことを一文にすると、こうなります。**ゲートは、通れない状態が常態のものに掛けると、作業全体が止まる**。ゲートを作るときは、厳しさより先に、掛ける相手を決める。手を動かして、初めて分かった所でした。

![](/images/claude-code-in-action-course-japanese/figure19.png)
*検査の対象を追跡済みの変更だけに絞ると、書きかけの記事でターンが止まらなくなります*


正直に書くと、まだやっていないことがあります。マーケットプレイスへの登録と、他のマシンへのインストールです。「配る」ところまでは、まだ行っていません。

### 無人実行が約3週間、誰にも気づかれず空振りしていた

最後は、うまくいかなかった話です。7節の実例として読んでください。

以前、毎朝自動で記事の下書きを作るジョブを、ヘッドレス（`claude -p`）で回していました。ある日から、認証（OAuth／オーオース。ログインを委任する仕組み）のセッションが切れます。それ以降ジョブは、毎朝起動しては、このエラーで即終了していました。

```text
Failed to authenticate: OAuth session expired
```

気づいたのは、約3週間後です。8月下旬から9月中旬まで。誰も見ていなかったし、失敗を知らせる仕組みも無かったんです。

毎朝きっちり起動して、毎朝きっちり失敗していたわけだ。

⚠️ 厄介なのは、何も壊れなかったことなんですよね。ジョブは予定どおりに起動していました。ただ、成果物が出ていなかっただけです。音のしない失敗は、見に行かない限り、見つかりません。

コースの言葉に当てはめると、2つともそのままでした。

- 「ヘッドレス実行はJSON結果と終了コードで検証する」
- 「見ていなかった分だけ検証する」

3週間見ていなかったのに、検証はゼロだったわけです。成果物が出ていないことを、終了コードで検知して、通知するべきでした。

![](/images/claude-code-in-action-course-japanese/figure20.png)
*毎朝起動しては認証エラーで終了する状態が、約3週間続いていました*

もう1つ、正直に書いておきます。今回も同じ理由で、手元のシェルからは `claude -p` が動きませんでした。だからこの記事には、ヘッドレスの実演がありません。

🚀 無人で回しているジョブがあるなら、最後にいつ成功したか、今日のうちに見てきて。

## 🧮 10. コース同士のズレ：数え方が違う

101の記事では、コースと製品のズレを書きました。今回は、コース同士でも数が違ったんです！🤔 権限モードも、フックのイベントも、CLAUDE.md の置き場も、です。

| 数えたもの | Claude Code 101 | 本コース | 公式ドキュメント |
| --- | --- | --- | --- |
| 権限モード | 3つ（既定/Auto-accept/Plan） | 6つ（Don't ask と Bypass permissions を含む） | 4つ（Shift+Tabで回る） |
| フックのイベント | 5つ | 約30 | ―― |
| CLAUDE.mdの置き場 | 2つ | 4つ | サブディレクトリとrulesも足して6段 |
| 自動検出をスキップするのは | ―― | `-p` | `--bare`（素の `-p` は全部読み込む） |

![](/images/claude-code-in-action-course-japanese/figure21.png)
*3つは数え方の違いで、自動検出のスキップだけは中身が食い違っています*

✅ 上の3つは間違いではなく、「どこまで数えるか」の違いでした。4つ目だけは中身が食い違っているので、ドキュメントの方を信じます。同じものを数えているのに、と最初は首をひねった。

💡 迷ったら、ドキュメントを開く。101のときの合言葉が、今回もそのまま使えましたね。

## 🎓 11. 授業に持っていく話と、次のコース

10月に、学生向けに「マルチエージェントでチームを組む」授業を担当します。このコースから持っていくものは、2つです。

1つ目。🔥 **お願いの層（CLAUDE.md・スキル）と、強制の層（フック）を分ける**。これを、説明するのではなく、手を動かして作らせます。exit 1 と exit 2 の違いは、学生が必ず踏む罠なので、そのまま演習にします。授業の演習、これで1つ決まった。

2つ目。Auto の分類器は「意図」、Stop フックは「正しさ」。✅ 安全と品質は別の仕組みで守る、という整理は、授業でそのまま使えます！

![](/images/claude-code-in-action-course-japanese/figure22.png)
*授業では、層を分けることと、安全と品質を別々に守ることを扱います*
