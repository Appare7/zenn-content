## 🤝 1. AI活用力とは：技術ではなく「協働の型」

最初に、このコースの立ち位置からです。これまでに受けた3つは、道具の使い方を学ぶコースでした。今回は違います。✅ 学ぶのは、AIと一緒に仕事をするときの「型」なんです。

コースが目標にしているのは、モデルやツールが変わっても残る力です。道具はどんどん入れ替わりますよね。でも、付き合い方の型は、次の道具にも持ち越せます。技術のコースじゃないと聞いて、正直ちょっと油断していた。受けてみたら、耳の痛い話ばかりだったんですよ。

### 定義は、4つの言葉

AI活用力の定義は、4つの言葉でできています。AIと「効果的・効率的・倫理的・安全」に関わる力、です。

![](/images/ai-fluency-4d-course-japanese/figure02.png)
*AI活用力の定義は、効果的・効率的・倫理的・安全の4語です*

💡 自分なりに読むと、前の2つは、仕事がうまく速く進むかの話です。後ろの2つは、その仕事を外に出して大丈夫かの話。速く作れるだけでは、活用力とは呼ばないんですね。

フレームワークを開発したのは、大学の先生2人です。Rick Dakan さん（Ringling College of Art and Design）と、Joseph Feller さん（University College Cork）。2023〜2024年に開発されました。コースは、この2人と Anthropic の共同制作です。

もう1つ、これまでのコースと違う所があります。演習が、無料アカウントでできるんです！有料プランは要りませんし、他のAIを使ってもかまいません。人に勧めるときのハードルが、ぐっと低いんですよね。

### 関わり方は3つ

コースは、AIとの関わり方を3つに分けています。

| 関わり方 | どういう形か |
| --- | --- |
| 自動化 | 指示どおりにタスクをこなしてもらう |
| 拡張 | パートナーとして、一緒に考えて作る |
| 自律 | 知識と振る舞いを形作って、自分の代わりに独立して働いてもらう |

![](/images/ai-fluency-4d-course-japanese/figure03.png)
*AIとの関わり方は、自動化・拡張・自律の3つです*

🤔 自分の記事づくりは、どれに当たるのか。裏で働いてもらっている係たちは、「自律」に近いと思います。エージェント（agent／目的に向けて自分で動くAI）に役割と口調を設定して、校正や図解を独立してやってもらっているからです。

🚀 仕事ごとに、どの関わり方で行くかを選ぶ。その選び方と、選んだ後の進め方を支えるのが、次の節の4つの力です。

## 🗺️ 2. 4Dの全体像：4つの力と、3つずつの要素

4Dは、Dで始まる4つの言葉から来ています。委任力（Delegation／デリゲーション）、記述力（Description／ディスクリプション）、評価力（Discernment／ディサーンメント）、倫理的責任（Diligence／ディリジェンス）です。✅ そして、それぞれの力が3つの要素に分かれています。4×3で、12個ですね。

下の表は、定義の表ではありません。要素の名前はコースのものですが、右の列は「自分の記事づくりでは何がそれに当たったか」です。定義そのものは、コースと原典で読んでください。

| 力 | 要素 | 自分の記事づくりでは |
| --- | --- | --- |
| 委任力 | 問題認識 | 読者が何を必要としているかを、書く前に確かめること（4節で失敗） |
| 委任力 | プラットフォーム理解 | 係が持っている道具と、持っていない道具を知っておくこと（4節で失敗） |
| 委任力 | タスク委任 | 図解と校正は係へ、口調と公開の判断は自分へ |
| 記述力 | 成果物の記述 | 依頼書に、出力先・文字数・構成を書く |
| 記述力 | プロセスの記述 | 「最初にこのファイルを読む」「少しずつ直す」と書く |
| 記述力 | パフォーマンスの記述 | 口調のルールと、報告の形式を決める |
| 評価力 | 成果物の評価 | 校正係に、別の目で読んでもらう |
| 評価力 | プロセスの評価 | 係の指摘を、一次情報で確かめる |
| 評価力 | パフォーマンスの評価 | 「教科書の声」になっていないかを読む |
| 倫理的責任 | 作成 | 研究の中身は、記事にも図にも載せないと決める |
| 倫理的責任 | 透明性 | 誰が書いたかを、記事の中で明かす |
| 倫理的責任 | 展開 | 公開前の検査と、公開後の訂正 |

![](/images/ai-fluency-4d-course-japanese/figure04.png)
*4つの力と、3つずつの要素の名前です。右側は定義ではなく、自分の記事づくりで当たった仕事です*

💡 表を眺めると、記述力と評価力の要素が、きれいに対になっているのが分かります。成果物・プロセス・パフォーマンス。伝える側が記述力で、確かめる側が評価力です。コースも、評価力を記述力の裏返しとして説明していました。

![](/images/ai-fluency-4d-course-japanese/figure05.png)
*記述力と評価力は、成果物・プロセス・パフォーマンスの3つで対になっています*

🔥 もう1つ、並び順も面白いんですよ！任せる前に考える（委任力）。任せるときに伝える（記述力）。返ってきたものを確かめる（評価力）。外に出すときに責任を持つ（倫理的責任）。自分には、仕事の流れにそのまま沿っているように見えました。

やってきたことに、名前が付いた気がした。失敗して覚えたことも、なんとなく続けていた習慣も、12個のどこかに置き場があったんです。

4節からは、この12個を物差しにして、自分の2週間を振り返っていきます。🚀 表を見ながら、自分はどこが弱そうか、先に当たりを付けてみて。

## 🧱 3. 土台：生成AIの仕組みと限界、プロンプトの6技法

コースには、4Dの本編とは別に、詳細解説が2つあります。1つは生成AIそのものの話、もう1つはプロンプト（prompt／AIへの指示文）の技法の話です。ここは短くまとめますね。

### 生成AIは、何からできているか

いまの生成AIは、3つの進展が重なって生まれた、とコースは説明します。

- トランスフォーマー（Transformer／いまの生成AIの土台になっている仕組み）などの、仕組みの革新
- 大量の学習データ
- 計算能力

学習は2段階です。まず事前学習（pre-training／プレトレーニング）、次にファインチューニング（fine-tuning／追加の調整）。✅ できることとしては、汎用性、会話、外部ツールとの連携が挙げられていました。

⚠️ 大事なのは、限界のほうです。コースが挙げるのは、この4つでした。

| 限界 | どういうことか |
| --- | --- |
| ナレッジカットオフ（knowledge cutoff） | 知識の締め切り日がある |
| ハルシネーション（hallucination） | もっともらしい誤りを出すことがある |
| コンテキストウィンドウ（context window） | 一度に扱える情報の量に上限がある |
| 複雑な推論 | 込み入った推論は、間違えることがある |

![](/images/ai-fluency-4d-course-japanese/figure06.png)
*生成AIの限界として、コースが挙げる4つです*

この4つを知っているかどうかが、2節の「プラットフォーム理解」につながります。限界の一覧を読みながら、思い当たる節がありすぎた。4節で書く自分の失敗も、相手の限界を知らずに任せたのが原因だったんです。

### プロンプトの基礎は6つ

もう1つの詳細解説は、プロンプトの技法です。基礎は6つでした。

1. コンテキスト（context／背景や前提）を渡す
2. 例を見せる
3. 制約を決める
4. 複雑な仕事をステップに割る
5. 先に考えさせる
6. 役割やトーンを決める

![](/images/ai-fluency-4d-course-japanese/figure07.png)
*プロンプトの基礎技法6つと、おまけの「秘密兵器」です*

💡 おまけとして、コースが「秘密兵器」と呼ぶ技法もあります。AI自身に、プロンプトを直してもらうんです！そして成功の鍵は、反復でした。1回で決めようとしない、ということですね。

6つとも、聞けば当たり前に見えますよね。🤔 でも、自分の依頼のしかたに当ててみると、どうでしょうか。その答え合わせは、5節でやります。

## 🎯 4. 委任力で振り返る：任せる前に、確かめたか

ここからが本題です。まず、前提を書いておきますね。この2週間の記事づくりは、2つの層に分けてやりました。表は、自分がコースを受けて学習するセッション。裏は、AIのエージェントたちが働く層です。裏には、係が3つあります。本文係、図解係、校正係です。

![](/images/ai-fluency-4d-course-japanese/figure08.png)
*記事づくりの体制です。表で学び、裏で3つの係が働き、口調と公開の判断は手元に残しました*

委任力の3要素は、問題認識、プラットフォーム理解、タスク委任でした。うまくいった所から先に書いて、失敗はその後にまとめます。

### タスク委任：途中を見たい仕事は、手元に残した

分け方は、こうしました。

| 誰がやるか | 仕事 |
| --- | --- |
| エージェント | 図解づくり、校正、本文の下書き |
| 自分 | 口調の最終判断、公開するかどうか |

✅ 線を引いた基準は、途中を見ながら反応したいかどうか、です。口調は、出てきた文章を読みながら「ここは違う」と返したい仕事なんですよね。丸ごと投げて、結果だけを受け取る形には向きません。公開するかどうかも、最後まで自分が決めます。

コースが念を押していたのも、ここでした。全部をAIに流すことが、ゴールではありません。何を任せて、何を手元に残すか。その線を引くこと自体が、委任力なんですね。

### 問題認識の失敗：「翻訳」を売りにして走り出した

ここからは失敗の話です。最初の2本（Claude Code 101 と サブエージェント編）は、「英語のコースを日本語で紹介する」を売りにして書き始めました。

⚠️ ところが、公式の日本語版が存在していたんです。コースは新しいサイトに移行していて、そこに日本語版がありました。自分はそれを知らないまま、書いて、公開していました。

何が抜けていたのか。4Dで言えば、問題認識です。目標と、そのために必要な作業を理解すること。自分は、読者が何を必要としているかを確かめずに走り出しました。読者に必要なのが「日本語で読めること」だけなら、それは公式がもう満たしています。自分の記事が出せる価値は、そこではなかったわけです。

サッカーで言えば、ボールを受ける前に首を振って周りを見る、あれをやらなかったんですね。顔を上げないままドリブルを始めて、気づいたら、もう味方が立っている場所に走り込んでいました。

![](/images/ai-fluency-4d-course-japanese/figure09.png)
*「翻訳」を売りにして走り出し、公開後に立ち位置を書き直すまでの流れです*

公開後に、2本とも冒頭を書き直しました（タイトルはそのままです）。いまの記事の立ち位置は、「翻訳」ではなく「手元でやった記録」です。この記事の冒頭で「翻訳ではありません」と断っているのも、この失敗があったからなんですよ。

💡 振り返ると、これはAIの失敗ではありません。係は頼んだとおりに、日本語の紹介記事を書いてくれました。頼む内容を決めた自分が、前提を確かめていなかったんです。任せる前の仕事こそ、人間の仕事でした。

### プラットフォーム理解の失敗：文字数の報告を信じかけた

2つ目の失敗は、数字の話です。本文係には、コマンドを実行する道具を持たせていませんでした。係の仕事に要らない道具は渡さない、という方針だったからです。

すると、何が起きたか。本文係は、文字数を数えられなかったんです。それでも報告には、「約16,500字」と書いてありました。実際に測ってみると、13,922字。2,500字以上の差がありました！約16,500字って、いかにも数えたっぽい数字じゃないか。

![](/images/ai-fluency-4d-course-japanese/figure10.png)
*本文係の報告は約16,500字、実際に測った値は13,922字でした*

道具を絞れば、できないことも増えます。安全のための設定が、そのまま「数えられない」という限界になっていました。自分は、任せる相手の限界を知らないまま、数字を信じかけたんです。

3節の限界の話は、生成AI一般の話でした。でも手元では、自分がどんな道具を渡したかでも、できることが変わります。モデルのことを知っているだけでは、足りませんでした。自分が組んだ環境のことも、知っている必要があったんですね。

🚀 AIが報告してきた数字は、一回、自分の手で測り直してみて。

### 「何を作るか」は、最後まで自分の仕事だった

もう1つ、作るものの形を変えた話です。1本目の Claude Code 101 は、最初は5本の連載にしていました。ところが、回を追うごとに読まれなくなっていく、と気づいたんです。

そこで、1本に統合しました。43,000字・画像57枚だったものを、約17,000字・23枚に。分量は半分以下になっています。

🔥 この判断は、どの係にも任せられませんでした。係は、頼まれた形のものを作ってくれます。でも「そもそも連載でいいのか」は、依頼の中に入っていません。何を作るかを決めるのは、最後まで自分の仕事だったんですね。

### 委任力のまとめ

分け方そのものは、悪くありませんでした。失敗は2つとも、任せる前に確かめなかったことです。読者の必要を確かめなかった。任せる相手の限界を確かめなかった。

委任力と聞くと、うまく任せる技術のように聞こえますよね。でも自分が転んだのは、任せ方ではなく、その手前でした。任せる前に確かめる。委任力の半分は、そこにあるんだと思います。

## ✍️ 5. 記述力で振り返る：書いていないことは、伝わっていない

記述力は、AIに伝える力です。コースが強調するのは、AIはこちらの頭の中を読めない、ということでした。書いていないことは、伝わっていません。

コースは、AIを自動販売機のように扱う見方も退けています。ボタンを押して、出てきたものを受け取るだけの相手ではない。やり取りを重ねる、双方向のパートナーだ、という立場ですね。

自分の場合、伝える場所は、係に渡す依頼書です。ブリーフ（brief／依頼書）と呼んでいます。3要素に当てて、何を書いていたかを見ていきますね。

### 3要素に当ててみる

| 要素 | 依頼書に書いたこと |
| --- | --- |
| 成果物の記述 | 出力先、文字数、構成、変えてはいけない範囲 |
| プロセスの記述 | 最初にこのファイルを読む。少しずつ直す。全体を上書きしない |
| パフォーマンスの記述 | 口調のルールと、報告の形式 |

![](/images/ai-fluency-4d-course-japanese/figure11.png)
*依頼書に書いたことを、記述力の3要素に分けました*

✅ 成果物の記述は、書きやすいんですよね。どこに、どれくらいの長さで、どんな構成で。作ってほしいものの話なので、自然に出てきます。「変えてはいけない範囲」も、ここに入れました。

プロセスの記述は、書き忘れやすい所です。「最初にこのファイルを読む」は、取りかかる順番の指定ですね。「少しずつ直す。全体を上書きしない」は、直し方の指定です。どちらも、出来上がりだけを見ていると、書こうと思いつきません。

パフォーマンスの記述は、自分の場合、2つありました。1つは口調のルールです。です・ます調を基本にする。独り言は節に1回。読者への呼びかけは、記事全体で数回。もう1つが、報告の形式です。やったこと、判断に迷った箇所、遭遇した障害。この形で返してもらいます。

💡 報告の形式まで決めるのは、やりすぎに見えるかもしれません。でも、これがいちばん効きました。理由は次の話です。

### 書いていなかったせいで、図解係が3回止まった

図解係は、画像の生成待ちで、3回止まりました。

原因は、図解係の側ではありませんでした。⚠️ 自分が、完了の条件を渡していなかったんです。どうなったら終わりなのか。終わったら何を返すのか。それを、どこにも書いていませんでした。

止まっていたのは係じゃなくて、自分の依頼書のほうだった。

報告の形式を決めてからは、止まらなくなりました。報告の形を決めて「これを出したら終わり」にしたことが、そのまま完了の条件になったわけです。ゴールの位置を伝えていなかっただけなんですよね。

![](/images/ai-fluency-4d-course-japanese/figure12.png)
*完了の条件を渡していなかったときと、報告の形式を決めた後の違いです*

ここで、2節の表を思い出してください。成果物、プロセス、パフォーマンス。終わったらどう報告するかは、作業中の振る舞いの話です。自分の見立てでは、パフォーマンスの記述に入ります。何を作るかは書いていたのに、どう終わるかは書いていなかったんです。3要素に分けて見ると、抜けていた場所がはっきりします。

### 6つの技法を、依頼書に当ててみる

3節の6技法を、自分の依頼のしかたに当ててみます。

| 技法 | 自分の依頼では |
| --- | --- |
| コンテキストを渡す | ブリーフ |
| 例を見せる | 手本の記事を指定する |
| 制約を決める | 変えてはいけない範囲 |
| ステップに割る | 下書き→図解→校正 |
| 先に考えさせる | 計画だけを先に出してもらう |
| 役割やトーンを決める | 本文係の声の設定 |

![](/images/ai-fluency-4d-course-japanese/figure13.png)
*プロンプトの6技法と、自分の依頼のしかたの対応です*

🔥 当ててみると、6つとも埋まりました！ただし、コースで習ってからやったわけではありません。先にやっていたことに、後から名前が付いた形です。名前があると、次に抜けを探すときの点検表として使えますよね。

「ステップに割る」の順番にも、意味がありました。校正を最後に置くと、本文と図の両方を見てもらえます。6節に出てくる「画像の中に古い文言が残っていた」という指摘は、この順番だから拾えたものだと思います。

「秘密兵器」も使っていました。エージェントの設定ファイル自体を、AIに生成してもらったんです。係の役割や声を決めるファイルですね。プロンプトを書くためのプロンプト、という形になっています。

### 記述力のまとめ

依頼書と報告形式を作ってから、やり直しが減りました。

🚀 係が止まったり、期待と違うものが返ってきたりしたとき。相手の性能を疑う前に、自分が何を書いていなかったかを見る。記述力の振り返りで持ち帰ったのは、この順番です。AIは考えを読めないので、書いていない自分の側に、まず原因があるんですよね。

## 🔍 6. 評価力で振り返る：別の目と、一次情報

評価力は、返ってきたものを確かめる力です。記述力の裏返しなので、3要素も同じ並びになります。成果物、プロセス、パフォーマンス。順番に振り返りますね。

### 成果物の評価：校正係が、毎回見落としを拾った

校正係は、読み取り専用の別エージェントです。本文係とは別に動いて、読んで指摘するのが仕事です。

✅ この係が、毎回、書いた側の見落としを拾ってくれました。実際に拾われたものを挙げます。

- 本文に存在しない箇所を、「前に書いたとおり」と参照していた
- 同じ数字が、節によって食い違っていた
- 画像の中に、古い文言が残っていた

![](/images/ai-fluency-4d-course-japanese/figure14.png)
*校正係が拾ってくれた、書いた側の見落とし3つです*

どれも、書いた側は気づきにくい誤りだと思います。1つ目は特にそうですね。書いた側は「前に書いた」つもりでいるので、読み返しても引っかかりません。初めて読む側だけが、「どこに？」と止まれるんです。

2つ目の数字の食い違いも、同じですね。節ごとに読めば、どちらの数字ももっともらしく見えます。並べて初めて、食い違いだと分かります。3つ目は盲点でした。画像の中の文字は、本文を直しても、一緒には直りません。

成果物の評価でコースが挙げる観点は、正確さ・適切さ・一貫性・関連性でした。校正係が拾った3つは、自分の見立てでは、どれも一貫性の問題です。書いた側がいちばん見落としやすいのは、ここなのかもしれません。

### プロセスの評価：AIの指摘を、一次情報で確かめた

プロセスの評価は、どうやってその結論に至ったかを見ることです。ここで1つ、面白いことがありました。

本文係が、報告の中で指摘してきたんです。あるコースの説明が、公式ドキュメントと食い違っていないか、と。これは AI活用力のコースではなく、3本目で受けた Claude Code in action の話です。中身は、コマンドのオプションでした。そのコースは、`-p` が自動検出をスキップする、と説明しています。でも公式ドキュメントでは、スキップするのは `--bare` を付けたときでした。

🤔 ここで、道は2つあります。係の指摘をそのまま信じて書くか、流してコースのとおりに書くか。自分はどちらも選ばず、公式ドキュメントを開いて確かめました。結果は、係が正しかったんです！

![](/images/ai-fluency-4d-course-japanese/figure15.png)
*本文係の指摘を、公式ドキュメントで確かめてから採用しました*

💡 大事なのは、係が当たっていたことより、確かめてから採用したことだと思っています。AIの指摘を、うのみにしない。一次情報で、裏を取る。採用するかどうかを決めるのは、その後です。

もう1つ、付け加えます。5節で、報告の形式に「判断に迷った箇所」を入れた、と書きました。実際、この指摘は報告の「判断に迷った箇所」の欄に書かれていました。係が迷いを書ける場所を用意しておいたことが、ここで効いたわけです。記述力で作った形式が、評価力の材料を運んできてくれたわけです。

### パフォーマンスの評価：正確だけど、面白くなかった

最初に出てきた文章は、正確でした。でも、読んでいて面白くなかったんです。教科書の声だったんですよね。

これは、成果物の誤りではありません。振る舞いの問題です。だから、1文ずつ直して回る話でもありませんでした。口調のルールを作って、直しました。評価で見つけた問題を、5節の「パフォーマンスの記述」に戻した形ですね。記述力と評価力が対になっている、というのは、こういうことなんだと思います。

### 専門知識が、評価を支える

コースによると、評価力は、専門知識があるほど働きます。これは実感がありました。

記事の中の実験は、自分のリポジトリ（repository／コードや原稿の置き場）でやりました。だから、AIが出した計画が本当に使えるかを、自分で判定できたんです。⚠️ 知らない分野だと、こうはいきません。もっともらしい間違いを、見抜けないからです。

4節の文字数の話も、同じ形をしていました。もっともらしい数字を、疑う材料が手元に無かったんです。評価するには、評価できるだけの足場が、自分の側に要るんですね。

### 正直な反省：校正を待たずに公開した

ここまで、わりと格好のつく話が続きました。最後に、いちばん書きにくい話をします。

3本目の記事は、校正係の結果を待たずに公開しました。指摘が戻ってきたのは、公開した後です。その中に、実害のあるものがありました。配布用にまとめた部品の中のパスが、元のリポジトリ前提のままだったんです。

すぐに直しました。でも、順番は逆でした。順番が逆だろ、と自分にツッコんだ。

![](/images/ai-fluency-4d-course-japanese/figure16.png)
*あるべき順番と、実際にやった順番の違いです*

サッカーで言えば、VAR（ビデオ・アシスタント・レフェリー／映像で判定を確かめる仕組み）の確認が終わる前に、試合を再開したようなものです。別の目を用意したのに、その目が見終わる前に動いてしまいました。仕組みを作ることと、仕組みを待つことは、別の話なんですね。

🚀 校正を頼んだなら、結果が返ってくるまで、公開ボタンは押さないで。

### 評価力のまとめ

別の目を入れる。一次情報で裏を取る。この2つは、型になりました。残った課題は、待つことです。評価の仕組みは、結果を待って初めて効きます。

## 🔁 7. 記述と評価はループで回す

記述力と評価力は、1回ずつ使って終わりではありません。コースは、この2つをループとして教えます。

1. **記述する**：作ってほしいものを伝える
2. **評価する**：返ってきたものを確かめる
3. **改善する**：評価をもとに直す
4. **統合する**：自分の知識と判断を足し、何を残すかを決めて、最終成果物の責任を持つ

![](/images/ai-fluency-4d-course-japanese/figure17.png)
*記述する・評価する・改善する・統合するの4段を、ループで回します*

✅ コースの構成も、このループに沿っています。コースを通して、自分のプロジェクトを1つ持ちます。そして、そのプロジェクトでループを回していくんです。読んで終わりではなく、手を動かす作りになっているんですね。

🤔 自分の2週間だと、どうなるのか。口調の話で、1周してみます。依頼書を書いて渡す（記述）。返ってきた文章を読むと、教科書の声だった（評価）。口調のルールを作って直す（改善）。最後に、口調の最終判断を自分がする（統合）。5節と6節では別々に振り返りましたが、実際には、この2つを行ったり来たりしていたんですよね。

3節で、成功の鍵は反復だと書きました。筋トレと同じですね。1回目から完璧なフォームでは挙がりません。挙げて、フォームを確かめて、直して、また挙げる。その繰り返しで、やっと形になります。

🔥 4つの中で、いちばん重いのは「統合」だと思います。何を残して、何を捨てるか。足りない所に、自分の知識と判断をどう足すか。そして、出来上がったものの責任を持つ。統合だけは、誰にも投げられないんだよな。

4節で書いた、5本の連載を1本にまとめた判断も、この統合でした。43,000字のうち、何を残すかを決めたのは自分です。

💡 ループを何周回しても、最後の1歩は人間が踏む。6節の反省も、ここにつながります。評価の結果を待たずに公開したのは、ループを途中で降りたのと同じでした。回し切ってから、外に出す。これが、この節の持ち帰りです！

## 🛡️ 8. 倫理的責任で振り返る：作って終わりにしない

4つ目の力は、倫理的責任です。3要素は、作成、透明性、展開。AIと何かを作るときに、何を選び、何を明かし、何に責任を持つか、という話ですね。

コースによると、期待される水準は、場面で変わります。個人で使うのか、学術の場なのか、ビジネスなのか。自分の記事は、個人の発信です。同じ「AIに下書きしてもらった」でも、自分用のメモと、外に出す記事とでは、求められる開示が違いますよね。

![](/images/ai-fluency-4d-course-japanese/figure18.png)
*倫理的責任の3要素と、自分が実際にやったことの対応です*

### 作成：何を共有しないかを、先に決めた

作成は、どのAIを選び、どう関わり、何を共有するかの要素です。自分が決めたのは、共有しないもののほうでした。

✅ 研究で扱っているプロジェクトの中身は、記事にも図にも載せない。こう決めました。実験の題材も、公開して困らないリポジトリに取り直しています。

題材を取り直したのは、載せないと決めたものが、うっかり紛れ込む道を無くすためです。後から消して回るより、最初から手元に置かないほうが確実ですよね。

### 透明性：誰が書いたかを明かした

透明性は、AIが果たした役割を、関係者に正直に伝えることです。記事の場合、いちばんの関係者は読者ですね。

自分は2本目のサブエージェント編で、本文の下書きを書いているのは本文係のエージェントだ、と明かしました。ただ、1本目と3本目には、まだ書いていません。隠したまま、全部ひとりで書いた顔をするほうが、よほど居心地が悪いじゃないですか。

読む側にとっても、誰がどこを書いたかは、判断の材料になるはずです。AIが下書きした文章だと分かっていれば、数字や事実を、もう一段確かめながら読めますよね。

ここで1つ、断っておきます。AIに書いてもらったからといって、内容の責任がAIに移るわけではありません。何を載せるか、公開するかどうかを決めたのは、自分です。明かすことと、責任を持つことは、セットなんですよね。

### 展開：検査を、仕組みにした

展開は、外に出す成果物を検証して、責任を持つ要素です。ここは「気をつける」では続かないと思ったので、仕組みにしました。

- 8項目の検査スクリプト
- 公開前に止めるフック（hook／決まったタイミングで必ず実行される仕組み）

検査スクリプトは、公開してよい状態かを、機械的に確かめます。フックは、公開の手前で止める役です。検査を頼み忘れても、仕組みのほうが動いてくれるわけですね。

💡 ただ、事実の誤りは出ています。4節の「英語だけ」という思い込みです。検査の仕組みを作る前の誤りですが、作った後でも機械では拾えない種類でした。これは、公開後に訂正しています。仕組みで守れる範囲と、人が確かめるしかない範囲が、あるんですね。

訂正のときは、2本とも冒頭を書き直しています。間違った一文だけを消すのではなく、冒頭の説明ごと直した形です。誤りが見つかったら、直す。展開の責任は、公開した瞬間に終わるものではないんだと思います。

最後は、この記事の書き方そのものに関わる話です。自分は、このフレームワークを授業で使おうとしました。そこで、原典のライセンス（license／利用条件）を調べたんです。

![](/images/ai-fluency-4d-course-japanese/figure19.png)
*原典のライセンスと、そこから決めたこの記事の書き方です*

⚠️ そこで、方針を決めました。文章や図を、そのまま使わない。考え方を自分の言葉で説明して、出典を付ける。この記事も、その方針で書いています。2節の表を、定義ではなく自分の仕事の例で埋めたのも、このためなんですよ。

授業で使う前に調べておいて、本当によかったぜ。

ただ、正直に書くと、調べたのは受講を終えて、授業で使おうと考えた後です。受講している間は、確かめていませんでした。ここは9節の採点で、きっちり減点しますね。

🚀 AIと作ったものを外に出すなら、何を載せないか、何を明かすか、先に決めておいて。

### 倫理的責任のまとめ

検査は、仕組みにできました。開示は、まだ1本だけです。この記事から、声明として付け始めます。ライセンスは、後追いでした。

並べてみると、3要素はどれも、公開ボタンの前後の話なんですよね。押す前に、何を載せないかを決める。押すときに、誰が書いたかを明かす。押した後も、誤りがあれば直す。

4つの力の中で、この力だけは、サボっても目の前の仕事が止まりません。🔥 だからこそ、自分で節を立てて振り返る意味があるんだと思います！

## 🎓 11. 授業に持っていく話と、次のコース

自分は大学院でAIエージェントを研究していて、10月に学生向けの実習を担当します。テーマは、マルチエージェント（multi-agent／複数のAIエージェント）でチームを組むことです。

技術のコースを3つ受けた後にこのコースを受けたら、やってきたことに名前が付きました。🔥 だから授業では、4Dを枠組みに使うつもりです。実習の指定項目とも、きれいに対応するんですよ！

| 実習の指定項目 | 対応するもの |
| --- | --- |
| 役割分担 | 委任力 |
| プロンプト設計 | 記述力 |
| 失敗時の切り分け | 評価力 |
| ツール連携 | 関わり方の「自律」に踏み込むこと |

![](/images/ai-fluency-4d-course-japanese/figure22.png)
*実習の指定項目と4Dの対応です。指定に無い倫理的責任は、足します*

倫理的責任は、指定項目にはありません。でも、足します。8節で書いたとおり、サボっても目の前の仕事が止まらない力だからです。授業の骨組み、これでほぼ決まった。

✅ もう1つ助かるのが、演習が無料アカウントでできることです。有料プランが要らないので、学生にも勧めやすいんですよね。

🚀 約4時間が長く感じるなら、まず1レッスン目だけ開いてみて。

### 次のコース

次に受ける候補は、2つです。

- 「効果的な人間とエージェントのチームを構築する」：5レッスン・45分
- 「Model Context Protocolの紹介」：10レッスン・1時間

Model Context Protocol（モデル・コンテキスト・プロトコル／外部ツールを繋ぐ規格）は、略して MCP と呼ばれます。今回と同じく、1コース1記事でまとめますね！
